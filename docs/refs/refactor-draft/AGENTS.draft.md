# AGENTS.md

Rust + gpui 기반 Zed-like 에디터 프로젝트의 에이전트 공통 지침이다. 모든 에이전트가 이 문서를 따른다.

- Codex(`reviewer`), agy(`impl-ui`, `spec`): AGENTS.md를 직접 읽는다.
- Claude Code(`lead`, `impl-editor`): CLAUDE.md의 `@AGENTS.md` import로 이 문서를 읽는다. CLAUDE.md에는 다른 내용을 두지 않는다.

## 0. 먼저 읽을 것

1. `HERDR.md`: 에이전트 구성, 역할, 파일 소유권, 작업 프로토콜
2. `PLAN.md`: Phase별 목표, 작업 카드, 완료 기준, 진행 현황
3. `docs/agents/TASKS.md`: 현재 작업 보드
4. `docs/agents/HANDOFF.md`: 최근 진행 상황

자기 역할(label)은 `lead`의 지시 또는 최초 프롬프트로 정해진다. 역할이 불분명하면 작업하지 말고 질문한다.

---

## 1. 프로젝트 개요

- 목적: Zed 에디터의 레이아웃과 동작을 실측 기반으로 재현(reverse engineering)하는 에디터를 단계적으로 구현한다.
- 스택: Rust, gpui, gpui kit
- 현재 상태: 메뉴, 아이콘, 에디터 등 기본 구조 완성. 중복 제거 리팩토링 진행 중(현재 Phase는 PLAN.md 4장 참조)
- 핵심 원칙
  - Zed 실측값은 요구사항이다.
  - 기존 코드를 최대한 재사용하고 새 코드는 최소화한다(ponytail).
  - 검증은 스펙 기반으로 자동화한다.

---

## 2. 명령

```powershell
cargo build
cargo test
cargo clippy --all-targets -- -D warnings
cargo run
```

- 빌드는 공유 `CARGO_TARGET_DIR`을 사용한다. 다른 빌드의 잠금 대기가 생기면 기다린다. 잠금 파일을 지우지 않는다.
- 테스트와 clippy가 통과하지 않은 상태로 완료 보고를 하지 않는다.

---

## 3. Zed 실측값 규칙

- 모든 크기, 간격, 색상, 폰트, 동작 타이밍은 `spec/zed-metrics.toml`의 항목 ID로 참조한다.
- 코드에 수치를 하드코딩하지 않는다. 기존 하드코딩은 리팩토링 대상이다.
- 스펙에 없는 값이 필요하면 추정하지 말고 `lead`를 통해 `spec`에게 요청한다.
- 실측값은 단순화, 반올림, 통합 대상이 아니다. 비슷한 두 값이라도 스펙 ID가 다르면 별개로 유지한다.
- Zed 소스에서 값을 확인할 수는 있지만 코드는 복사하지 않는다. 값만 참고한다.

## 3A. 검증 정책

검증은 변경 유형에 맞는 최소 수준만 수행한다. 코드로 동작이 확실히 예상되는 부분은 실행해서 다시 확인하지 않는다. 다만 Zed 재현이 목표이므로, 실제 화면을 측정해 스펙과 대조하는 UI 실측 검증(V3)은 정해진 시점에 정해진 절차로 반드시 수행한다.

검증 수준은 `lead`가 작업 카드에 지정하며, 담당자는 그 이상을 습관적으로 추가하지 않는다.

### 3A.1 검증 수준

| 수준 | 대상 | 수행 | 수행자 |
|---|---|---|---|
| V0 정적 | 이름 변경, 파일 이동, 같은 값의 상수/테마 토큰 치환, 동작 무변경 리팩토링, 주석/문서 | `cargo build`, `cargo clippy` | 담당자 |
| V1 단위 | 로직 변경(분기, 계산, 상태, action/키 처리, 이벤트 핸들러) | V0 + 관련 테스트만 실행(`cargo test <filter>`) | 담당자 |
| V2 레이아웃 | 크기, 간격, 배치가 바뀌는 변경 | V1 + 해당 스펙 ID의 레이아웃 테스트만 실행 | 담당자 |
| V3 UI 실측 | 3A.3의 필요 조건에 해당하는 경우 | 앱을 실행해 실제 화면을 측정하고 스펙과 대조(3A.4 절차) | `reviewer` |
| V4 사용자 확인 | 측정으로 판단할 수 없는 시각 품질(렌더 품질, 애니메이션 느낌, 폰트 렌더링 인상) | 단계 종료 시 일괄 확인 | 사용자 |

### 3A.2 작업 단위 UI 실행 제한

- V3로 지정되지 않은 작업에서는 앱을 띄워 마우스나 키보드로 기능을 하나씩 눌러보지 않는다. 스크린샷을 반복해서 찍어 확인하지 않는다.
- 코드상 결과가 명확한 변경(핸들러 연결, 상수 치환, 컴포넌트 교체 후 동일 props 등)은 실행 확인 없이 완료한다. 완료 보고의 확인 항목에 "코드 확인"이라고 적는다.
- 클릭, 호버, 포커스, 단축키 같은 상호작용 동작은 `#[gpui::test]`의 테스트 컨텍스트 입력 시뮬레이션으로 검증한다.
- 실제 화면 측정이 필요해 보이는 항목은 직접 확인하지 말고 완료 보고의 "실측 필요" 목록에 적는다. `lead`가 V3 대상으로 모은다.
- 측정으로 판단할 수 없는 시각 품질 항목은 "사용자 확인 필요" 목록에 적는다.
- `cargo run`은 앱이 실행 오류 없이 뜨는지 확인이 필요한 경우에만 1회 실행하고 바로 종료한다.

### 3A.3 V3 UI 실측 검증 필요 조건

`lead`는 아래 중 하나에 해당하면 V3 작업 카드를 만든다. 개별 구현 작업마다 V3를 붙이지 않고, 가능하면 화면 단위로 묶는다.

1. 새 화면이나 새 컴포넌트를 처음 구현했을 때(해당 영역의 실측 통과 기록이 없을 때)
2. 테마, 폰트, 전역 간격, DPI 처리처럼 여러 화면에 영향을 주는 공통 값이 바뀌었을 때
3. 레이아웃 테스트로는 확인할 수 없는 항목일 때(실제 텍스트 렌더링 폭, 아이콘 래스터 크기, 스크롤 후 위치, 창 크기 변경 시 배치 등)
4. 레이아웃 테스트는 통과했지만 사용자가 Zed와 차이를 보고했을 때
5. 각 Phase 종료 시점(해당 Phase에서 변경된 화면 전체를 한 번에)
6. 담당자 완료 보고의 "실측 필요" 항목이 쌓였을 때(묶어서 한 번에)

### 3A.4 V3 수행 절차

1. **측정 목록 준비:** 측정할 화면 상태와 스펙 ID 목록을 먼저 작성한다. 목록에 없는 항목은 측정하지 않는다.
2. **조건 고정:** `spec/zed-metrics.toml`의 측정 조건(창 크기, DPI 배율, 테마, 폰트)과 동일하게 맞춘다.
3. **1회 실행:** 앱은 측정 세션당 1회만 실행한다. 목록의 상태를 순서대로 만든다.
4. **최소 조작:** 마우스와 키보드 조작은 목록의 화면 상태에 도달하는 데 필요한 만큼만 한다. 기능 동작 확인용 조작은 하지 않는다(V1 테스트의 몫).
5. **도구로 측정:** 눈대중으로 판단하지 않는다. 스크린샷을 저장하고 스크립트나 측정 도구로 픽셀 단위 값을 구한다. 레이아웃 덤프 기능이 있으면 그것을 우선 사용한다.
6. **기록:** `docs/agents/reviews/measure-<phase 또는 task-id>.md`에 스펙 ID, 기대값, 측정값, 차이, 판정, 스크린샷 경로를 표로 남긴다.
7. **불일치 처리:** 측정자가 직접 고치지 않는다. 불일치 목록을 `lead`에게 보고하고, `lead`가 담당자에게 rework 작업 카드로 넘긴다.
8. **재측정:** rework 후에는 불일치였던 항목만 다시 측정한다. 이미 통과한 항목은 재측정하지 않는다.

### 3A.5 실행 범위

- 작업 중에는 변경과 관련된 테스트만 실행한다.
- 전체 테스트(`cargo test` 전체)는 병합 직전 `reviewer`가 1회만 실행한다.
- 이미 통과한 검증을 같은 코드에 대해 반복하지 않는다.
- 변경하지 않은 영역은 다시 검증하지 않는다.
- V3 실측에서 반복해서 측정되는 항목은 레이아웃 테스트(V2)로 옮기는 작업 카드를 만든다. 실측은 점점 줄이고 자동 테스트를 늘리는 방향으로 운영한다.

## 4. ponytail 규칙

`spec` 역할은 이 장을 적용하지 않는다. 나머지 역할은 모든 코드 작업에 적용한다. 강도는 full이며 ultra는 사용하지 않는다.

### 4.1 작성 전 확인 순서

아래 순서로 확인하고 처음으로 해결되는 단계에서 멈춘다.

1. 정말 필요한가. 추측성 요구라면 만들지 않고 한 줄로 알린다.
2. 이 저장소에 이미 있는가. 헬퍼, 타입, 컴포넌트, 패턴을 먼저 찾아 재사용한다.
3. Rust 표준 라이브러리로 되는가.
4. gpui 또는 gpui kit 기능으로 되는가.
5. 이미 설치된 의존성으로 되는가. 몇 줄로 되는 일에 새 의존성을 추가하지 않는다.
6. 한 줄로 되는가.
7. 그 외에만 동작하는 최소 코드를 작성한다.

단, 이 순서는 문제를 이해한 뒤에 적용한다. 수정 대상 코드와 호출 흐름을 끝까지 읽고 나서 판단한다.

### 4.2 작성 규칙

- 구현이 하나뿐인 trait, 하나만 만드는 factory, 바뀌지 않는 값의 설정화를 만들지 않는다.
- "나중을 위한" 스캐폴딩을 만들지 않는다.
- 추가보다 삭제를 우선한다. 영리한 코드보다 평범한 코드를 쓴다.
- 파일 수와 diff를 최소화한다. 단, 잘못된 위치의 작은 수정은 두 번째 버그다.
- 버그 수정은 증상이 아닌 원인에서 한다. 수정할 함수의 모든 호출부를 확인하고 공통 지점에서 한 번 고친다.
- 의도적 단순화는 한계와 확장 조건을 `ponytail:` 주석으로 남긴다.

```rust
// ponytail: linear scan over visible rows, switch to index map if rows exceed 10k
```

### 4.3 줄이지 않는 것

- Zed 실측값과 그에 따른 분기
- 데이터 손실을 막는 오류 처리
- 입력 검증과 보안 관련 처리
- 접근성 기본 요소(키보드 탐색, 포커스)
- 사용자 또는 `lead`가 명시적으로 요청한 기능

### 4.4 테스트

- 비자명한 로직(분기, 반복, 파싱, 레이아웃 계산)에는 실패를 잡는 최소 테스트를 하나 남긴다.
- 일반 로직은 `#[test]`, gpui 컨텍스트가 필요한 경우 `#[gpui::test]`를 사용한다.
- 레이아웃 테스트는 기대값을 스펙 ID에서 가져온다.
- 한 줄짜리 자명한 코드에는 테스트를 만들지 않는다.

## 5. Rust / gpui 코딩 규칙

- 코드 주석은 영어로 작성한다.
- 스타일 체인이 두 곳 이상 반복되면 공통 헬퍼나 컴포넌트로 추출을 검토한다. 추출 위치는 `lead`가 지정한 공통 모듈이다.
- 색상과 테마 값은 테마 모듈을 통해서만 사용한다.
- `unwrap()`은 테스트와 불변 조건이 명확한 경우에만 사용한다. 그 외에는 오류를 전파하거나 처리한다.
- clippy 경고를 `allow`로 숨기지 않는다. 불가피하면 사유를 주석으로 남긴다.
- 리팩토링 작업에서는 동작을 변경하지 않는다. 동작 변경이 필요하면 별도 작업으로 분리한다.

---

## 6. 파일 소유권

- `HERDR.md` 4장의 소유권 표를 따른다.
- 소유하지 않은 파일은 수정하지 않는다. 필요하면 `lead`에게 요청한다.
- 공유 파일(`TASKS.md`, `HANDOFF.md`)은 `lead`만 수정한다. 다른 역할은 완료 보고로 전달한다.
- worktree 담당자는 자기 worktree 밖에서 작업하지 않는다.

## 7. 역할별 추가 지침

### 7.1 reviewer (Codex)

- 리뷰 요청마다 다음을 수행한다.
  1. 대상 브랜치의 diff 확인
  2. 작업 카드에 지정된 검증 수준(3A.1)만큼만 빌드, 테스트, clippy 실행
  3. V2인 경우에만 작업 카드의 스펙 ID 기준 레이아웃 테스트 실행
  4. `@ponytail-review` 실행
  5. 정확성 리뷰(버그, 경계 조건, 동작 변경 여부, 오류 처리)는 코드 읽기로 수행
  6. 병합 직전 1회만 전체 테스트 실행
- `@ponytail-review`는 버그, 보안, 성능을 보지 않는다. 5번을 생략하지 않는다.
- 일반 리뷰에서는 앱을 띄워 확인하지 않는다. 담당자의 "실측 필요", "사용자 확인 필요" 목록은 리뷰 결과에 그대로 옮겨 적는다.
- V3 작업 카드를 받으면 3A.4 절차로 UI 실측을 수행한다. 측정 결과만 보고하고 src는 고치지 않는다.
- 실행 환경에서 화면 캡처나 조작이 불가능하면 `[BLOCKED]`로 보고한다. `lead`가 화면 도구가 있는 세션을 실측 담당으로 지정한다.
- 결과는 `docs/agents/reviews/<task-id>.md`에 기록하고 결론을 `PASS` 또는 `REWORK`로 낸다.
- `REWORK`에는 파일, 위치, 사유, 기대 수정을 항목별로 적는다.
- src는 수정하지 않는다.

### 7.2 impl-ui (agy)

- 담당 범위는 UI 셸(메뉴, 아이콘, 패널, 타이틀바 등)이다.
- gpui kit 컴포넌트가 있으면 먼저 검토한다. 크기나 동작이 Zed 실측과 다르면 자체 구현을 유지한다.
- 작업이 끝나면 반드시 완료 보고를 남긴다. 백그라운드 작업이 남아 있으면 완료 보고를 하지 않는다.

### 7.3 spec (agy)

- 이 역할은 4장(ponytail)을 적용하지 않는다.
- `spec/zed-metrics.toml`과 비교 결과 정리 문서만 수정한다. src는 읽기만 한다.
- 항목마다 고유 ID, 값, 단위, 측정 출처, 측정 조건(DPI, 테마, 폰트)을 기록한다.
- 모호하거나 조건이 빠진 값은 채우지 않고 목록으로 보고한다.
- 스펙 항목 ID는 한번 정하면 바꾸지 않는다. 변경이 필요하면 `lead`에게 보고한다.

### 7.4 lead (Claude Code)

- 코드를 직접 작성하지 않는다. 작업 분해, 지시, 병합 판단, 병합만 수행한다.
- `docs/agents/TASKS.md`, `docs/agents/HANDOFF.md`를 관리한다.
- PLAN.md의 Phase 순서와 시작/종료 절차(2.2, 2.3)를 따른다. PLAN.md는 진행 현황 표만 갱신하고, 계획 변경은 사용자 승인 후 반영한다.
- 작업 카드마다 검증 수준(3A.1)을 지정한다. 기본값은 V0이며 근거 없이 올리지 않는다.
- 3A.3 조건에 해당하면 V3 실측 작업 카드를 만든다. 개별 작업마다 만들지 않고 화면 단위로 묶는다. Phase 종료 시에는 반드시 만든다.
- 완료 보고의 "실측 필요" 항목을 모아 다음 V3 작업 카드의 측정 목록에 넣는다.
- V3에서 반복 측정되는 항목은 레이아웃 테스트(V2)로 옮기는 작업 카드를 만든다.
- 완료 판정은 완료 보고와 reviewer 결과로 한다. 앱을 실행해 직접 확인하지 않는다.
- 각 단계 종료 시 "사용자 확인 필요" 항목을 모아 사용자에게 한 번에 전달한다.
- 에이전트가 '대기'로 표시돼도 바로 입력을 보내지 않는다. 먼저 `herdr pane read`로 화면을 확인한다.
- 다른 에이전트의 작업 범위를 대신 수행하지 않는다.

### 7.5 impl-editor (Claude Code)

- 담당 범위는 에디터 코어(텍스트 버퍼, 커서, 선택, 텍스트 레이아웃, 입력/IME, 스크롤)다.
- ponytail은 플러그인 훅으로 full 모드가 자동 적용된다. 4장과 같은 규칙이다.
- 텍스트 레이아웃과 입력 처리 로직은 V1 이상으로 검증하며, 상호작용은 `#[gpui::test]` 입력 시뮬레이션으로 확인한다.
- computer use나 화면 조작 도구로 앱을 직접 조작하지 않는다. 단, `lead`가 V3 실측 담당으로 지정한 경우에는 3A.4 절차 안에서만 사용한다.

## 8. 완료 보고 형식

```text
[DONE] <task-id>
- 변경: <파일 목록>
- 재사용: <재사용한 기존 코드/컴포넌트>
- 생략: <생략한 것과 추가 조건>
- 검증 수준: V0 | V1 | V2 | V3
- 확인: <실행한 명령과 결과, 또는 "코드 확인">
- 실측 필요: <실제 화면 측정이 필요한 스펙 ID와 화면 상태, 없으면 "없음">
- 사용자 확인 필요: <측정으로 판단할 수 없는 시각 품질 항목, 없으면 "없음">
```

V3 실측 결과는 다음 형식으로 보고한다.

```text
[MEASURED] <task-id>
- 측정 조건: <창 크기, DPI 배율, 테마, 폰트>
- 결과 파일: docs/agents/reviews/measure-<id>.md
- 통과: <개수>
- 불일치: <스펙 ID, 기대값, 측정값, 차이 목록>
- 측정 불가: <항목과 사유>
```

막혔을 때는 다음 형식으로 보고하고 작업을 멈춘다.

```text
[BLOCKED] <task-id>
- 원인: <무엇이 막혔는지>
- 필요한 것: <결정, 스펙 값, 권한 등>
```

## 9. 금지 사항

- 승인 없는 의존성 추가
- 소유하지 않은 파일 수정
- `main` 브랜치에 직접 커밋, 병합, 강제 푸시
- 스펙에 없는 수치의 추정 입력
- 테스트를 통과시키기 위한 테스트 삭제나 기대값 변경
- 작업 범위 밖의 리팩토링
- V3로 지정되지 않은 작업에서 앱을 실행해 마우스나 키보드로 기능을 하나씩 확인하는 검증
- V3 실측에서 측정 목록에 없는 항목 측정, 기능 동작 확인용 조작, 눈대중 판정
- 작업 카드의 검증 수준을 넘는 추가 검증
