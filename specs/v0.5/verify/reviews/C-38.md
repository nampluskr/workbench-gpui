## 2. 주요 핵심 항목 심층 점검

### 2.1 K-35 `nav_history.rs` 기록 규칙 vs SPEC R-10 표
- **10줄 이동 기준 (`MIN_NAVIGATION_HISTORY_ROW_DELTA = 10`)**:
  - `observe()`에서 이전 위치(`old`)와 현재 위치(`now`)의 줄 차이를 검사:
    ```rust
    old.path != n.path || n.row.abs_diff(old.row) >= MIN_NAVIGATION_HISTORY_ROW_DELTA
    ```
    10줄 이상일 때만 `record(old)`를 호출하고, 9줄 이하 커서 이동은 기록하지 않음. Zed `crates/editor/src/editor.rs:307` 기준 완벽 일치.
- **같은 자리 중복 제거 (`same_place`)**:
  - `push_into()`에서 `stack.retain(|e| !e.same_place(&entry))`를 수행하여 동일한 파일·동일한 줄의 이전 기록을 교체/제거.
- **새 기록 시 forward 스택 초기화**:
  - `record()`에서 `self.forward.clear()`를 명시적으로 호출하여 분기 탐색 시 앞 스택 비움 보장.
- **1024개 상한 관리**:
  - `MAX_NAVIGATION_HISTORY_LEN = 1024`로 지정하고, 스택 크기가 초과하면 `stack.pop_front()`로 가장 오래된 항목 제거.
- **닫힌 탭 복원 및 유효하지 않은 파일 건너뛰기**:
  - `step(forward, usable)`에서 닫힌 탭도 스택에 유지되며, `usable(&entry)` 콜백으로 파일 존재 여부를 확인하고 없으면 스택에서 제거 후 다음 항목으로 자동 폴백. `pane_group.rs`의 `navigate()`에서 닫힌 파일이면 `self.open(&entry.path, false, window, cx)`로 자동 재오픈 후 커서 복원.
- **단위 테스트**: `k35_the_nine_zed_steps` 등 9개 전용 테스트로 Zed 9단계 조작 시나리오 검증 완료.

### 2.2 K-37 `window.refresh()` 렌더 반복 여부
- **검증 위치**: `src/ui/layout.rs:341-348`, `on_children_prepainted` 훅
- **동작 분석**:
  ```rust
  fn after_layout(&self) -> bool {
      if let Some(ix) = self.pending.take() {
          self.handle.scroll_to_item(ix);
          true
      } else {
          false
      }
  }
  ```
  - `self.pending`은 `Cell<Option<usize>>` 구조이며, `.take()` 호출 즉시 값을 비움(`None`).
  - 활성 탭이 바뀌거나 탭 수가 바뀔 때만 `follow()`에 의해 `pending`에 새 인덱스가 설정됨.
  - 첫 번째 prepaint 프레임에서 `.take()`가 성공하여 `window.refresh()`가 1회 호출되고, 다음 렌더 프레임에서는 `pending`이 이미 `None`이므로 `after_layout()`이 `false`를 반환.
  - 따라서 **렌더마다 `window.refresh()`가 반복되지 않고 대기 요청이 있을 때 1회만 호출됨**이 코드로 완벽히 보장됨.

### 2.3 K-34 `heading_trail` 펜스 처리
- **검증 위치**: `src/ui/breadcrumb.rs:24-55`
- **동작 분석**:
  - 코드 블록 펜스(` ``` ` 또는 ` ~~~ `)를 감지하여 `fence: Option<char>` 상태를 토글.
  - 펜스 내부(`fence.is_some()`)의 라인은 `#` 기호가 있더라도 헤딩으로 파싱하지 않고 건너뜀.
  - ATX 헤딩(`# `부터 `###### `)만 인식하고 4칸 이상 들여쓰기된 라인은 건너뜀.
  - 의도적 단순화 범위에 대해 ponytail 규칙에 따라 명확한 `shortcut:` 주석 남김:
    ```rust
    // shortcut: ATX headings only (no setext ===/--- underlines), fences toggle on any line starting with three
    // backticks or tildes, # inside HTML blocks is read as a heading; upgrade with a real Markdown parser if these show up.
    ```

### 2.4 K-34 워크스페이스 외부 파일 (단일 파일 워크트리) 표시: 앱 vs tauri vs Zed 4304dec
- **배경**:

- **Zed 4304dec 소스 확인 (`%TEMP%\zed-src-4304dec7`)**:
  - `crates/editor/src/editor.rs:11685` (`breadcrumbs_inner`):
    ```rust
    let text = self.breadcrumb_header.clone().unwrap_or_else(|| {
        buffer
            .read(cx)
            .snapshot()
            .resolve_file_path(
                self.project
                    .as_ref()
                    .map(|project| project.read(cx).visible_worktrees(cx).count() > 1)
                    .unwrap_or_default(),

            .unwrap_or_else(|| multi_buffer.title(cx).to_string())

    ```
  - `crates/language/src/buffer.rs` (`resolve_file_path`):
    ```rust
    pub fn resolve_file_path(&self, include_root: bool, cx: &App) -> Option<String> {
        if let Some(file) = self.file() {
            if file.path().file_name().is_none() || include_root {
                Some(file.full_path(cx).to_string_lossy().into_owned())
            } else {
                Some(file.path().display(file.path_style(cx)).to_string())
            }
        } else {
            None
        }
    }
    ```
  - **분석 결과**:
    - Zed에서 프로젝트 폴더 밖의 파일을 열면 해당 단일 파일 자체가 단일 파일 워크트리(single-file worktree)가 되며, `file.path()`는 루트(빈 경로)가 됩니다.
    - `full_path()`는 `root_name`(즉, 파일명 자체)을 반환하며, `multi_buffer.title()` 역시 파일명을 반환합니다.
    - 즉, **Zed의 실제 동작은 긴 절대 경로가 아니라 파일 이름만 표시**하는 것입니다.
    - 따라서 `workbench-gpui`의 구현(`path.file_name()`)이 Zed 원본 동작과 일치하며, 전체 경로를 표시한 `workbench-tauri`가 오히려 Zed와 다른 동작임이 확인되었습니다.
