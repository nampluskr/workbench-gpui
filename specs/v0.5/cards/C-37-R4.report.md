## 1. 5차 오류 원인 및 해결 상세

### 1.1 step1·2·5 앞 창 얻기 실패 (`FATAL: setup - Failed to bring app window ... to foreground`)
- **원인**: Windows OS는 백그라운드 프로세스(터미널의 `pwsh`)가 `SetForegroundWindow`로 다른 창을 포그라운드로 강제 전환하는 것을 방지(foreground lock)합니다. 기존 스크립트는 `setup`에서 `Ensure-Foreground`가 즉시 앞 창을 얻지 못하면 `FATAL`을 발생시켜 스크립트를 중단했습니다.
- **해결**:
  1. **마우스 입력 가드 (`Assert-MouseInput`)**:
     - 클릭 대상 화면 좌표 `(targetScreenX, targetScreenY)`에 대해 `WindowFromPoint`로 대상 윈도우 핸들(`$hTarget`)을 획득하고, `GetAncestor($hTarget, GA_ROOT)`로 최상위 루트 윈도우(`$hRoot`)를 구합니다.
     - `GetWindowThreadProcessId`로 해당 윈도우의 PID를 조회하여 세션에서 띄운 `$script:appPid`와 일치하는지 검증합니다.
     - 좌표의 최상위 창과 PID가 앱과 일치하면 클릭 이벤트는 온전히 앱으로 전달되며, 사용자가 마우스로 창을 누른 것과 동일하게 Windows가 자연스럽게 해당 창을 포그라운드로 활성화합니다.
     - 만약 다른 창이 앱을 덮고 있거나 PID가 다르면 입력을 발송하지 않고 `FAIL`을 기록하며 단계를 중단합니다.
  2. **키 입력 가드 (`Assert-KeyInput`)**:
     - 키 입력 전 `GetForegroundWindow() == $script:appHwnd`를 확인합니다.
     - 만약 앞 창이 아니면, 위 마우스 가드를 통과하는 안전한 위치(에디터 영역 중앙 `ClientToScreen(700, 400)`)에 안전 활성화 클릭을 1회 수행한 뒤 `GetForegroundWindow()`를 재확인합니다. 재확인 후에도 앞 창이 아니면 입력을 차단하고 `FAIL` 처리합니다.
  3. **비입력 Z-순서 상승 (`Ensure-Foreground`)**:
     - 창 가림을 방지하기 위해 `ShowWindow(SW_RESTORE=9)`, `SetWindowPos(HWND_TOP, 0, 0, 0, 0, SWP_NOMOVE|SWP_NOSIZE|SWP_SHOWWINDOW)`, `SetForegroundWindow`를 순차 호출합니다.
     - `HWND_TOPMOST`는 사용자의 작업 환경을 침범하므로 사용하지 않고 `HWND_TOP`만 사용합니다.
     - 띄운 PID 창에만 Z-순서 상승을 적용하도록 대상 창 PID 검증을 추가했습니다.
     - Z-order 상승 시도 로그(`[ELEVATE]`)와 실제 앞 창 도달 여부 확인 로그(`[VERIFY-FG]`)를 분리하여 가시성을 확보했습니다.
  4. **setup 비치명화**:
     - `setup` 단계에서 초기 윈도우 로드 직후 `Ensure-Foreground` 불일치 시 `FATAL throw`를 제거하고, `project-empty-open` 또는 에디터 영역 마우스 클릭을 통해 자연스럽게 활성화되도록 개선했습니다.
  5. **마우스 휠 & 뒤로 가드 (`Assert-MouseWheelAndBack`)**:
     - 마우스 휠(`Safe-MouseWheel`)과 마우스 뒤로가기(`Safe-MouseBack`)는 마우스 가드(점의 창=앱, PID 일치)와 키 가드(앞 창=앱) **둘 다** 만족할 때에만 이벤트를 발송하도록 이중 가드를 적용했습니다.

### 1.2 step3 `'if' 용어는 cmdlet... 인식되지 않습니다` 해결
- **발생 위치**: `tools/measure/order09-v3.ps1` 기존 1314행 부근
- **원인**:
  ```powershell
  Wait-NextSnapshot $Out (if ($immediateSnap) { $immediateSnap.seq } else { $prevSeq }) 1000
  ```
  PowerShell에서는 함수 인자에 `(if (...) { ... } else { ... })` 표현식을 직접 넘기면 파서가 `if`를 일반 cmdlet/명령어 호출로 잘못 파싱하여 `'if' 용어는 cmdlet, 함수, 스크립트 파일 또는 실행할 수 있는 프로그램 이름으로 인식되지 않습니다` 오류가 발생합니다.
- **해결**:
  표현식을 함수 호출 전에 명시적 로컬 변수로 분리 추출했습니다.
  ```powershell
  $nextWaitSeq = if ($immediateSnap) { $immediateSnap.seq } else { $prevSeq }
  $snap = Wait-NextSnapshot $Out $nextWaitSeq 1000
  ```

### 1.3 step4 `'modifiers' ... System.Object[] ... System.UInt16` 해결
- **발생 위치**: `tools/measure/order09-v3.ps1`의 `Safe-KeyCombo` 호출부 전체
- **원인**:
  1. PowerShell 함수 호출 문법은 공백 구분(`Func arg1 arg2`)이지만, 코드에서 쉼표(`Safe-KeyCombo @(0x11), 0xDC`)를 사용하여 `(@(0x11), 0xDC)` 전체가 첫 번째 매개변수(`$modifiers`)로 묶여 전달되었습니다.
  2. 기존 서명 `[ushort[]]$modifiers`에 배열과 정수가 섞인 `Object[]`가 바인딩되면서 요소 변환 실패 예외가 발생했습니다.
- **해결**:
  1. `Safe-KeyCombo` 함수 서명을 `($modifiers, [int]$key = 0)`으로 변경하고, 쉼표 호출 구문(`Safe-KeyCombo @(0x11), 0x21`)으로 묶여 전달된 경우에도 자동으로 `$modifiers`와 `$key`를 올바르게 분리하도록 방어 로직을 내장했습니다.
  2. `$modifiers`가 단일 값, 정수 배열, 중첩 배열 등 어떤 형태로 전달되더라도 내부에서 `List[ushort]`로 안전하게 평탄화(flattening)하여 Win32 native API에 전달하도록 개선했습니다.
  3. 모든 호출부(`step3`, `step4`, `step5`)에서 쉼표를 제거하고 표준 PowerShell 공백 구분 문법(`Safe-KeyCombo @(0x11) 0x24` 등)으로 통일했습니다.
