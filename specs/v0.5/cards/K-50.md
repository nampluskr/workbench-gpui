# K-50 — 파일을 처음 열 때 전체 파싱만 background executor로
core 결정: 파일을 처음 열 때 하는 **전체 파싱만** gpui `background_executor`로 옮긴다. 그동안 평문으로 보이고, 끝나면 강조(Zed와 같은 모양 — `buffer.rs` 1177·1943~2010, 값·규칙만). **편집 중 증분 파싱은 지금처럼 동기**로 둔다(K-49). 이유: tauri는 4.5만 줄 TS를 열 때 UI 정지 약 0.1초, gpui는 1.4초(K-49 첫 파싱).
1. 대상: `set_value`(파일 열기·다시 읽기) 뒤 새 하이라이터의 첫 전체 파싱(루트 + 주입 층). 백그라운드에서 파싱한 결과(트리·층)를 UI 스레드에서 하이라이터에 넣고 편집기를 다시 그리게 한다. 그 사이 `runs`는 빈 결과(평문), 경로 줄 심볼도 빈 목록.
2. 경쟁: 백그라운드 파싱 중 편집이 들어오면 — 가장 작은 안전한 방법을 고른다(예: 결과가 올 때 글자 버전이 다르면 버리고 지금 글자로 다시 백그라운드 파싱, 또는 결과를 받은 뒤 그동안의 편집을 적용). 파싱 중 파일을 닫거나 다른 파일로 바꾸면 결과를 버린다. 패닉·누수 없게. 선택과 이유를 보고에.
3. 작은 파일: 파싱이 짧으면(Zed처럼 짧은 동기 시도 — 시간 제한 값은 Zed 소스 값) 동기로 끝내 깜박임이 없게. 
4. 미리보기 코드 블록 하이라이터·편집 중 증분 파싱은 바꾸지 않는다. vendor/gpui-base 변경 없음, 의존성 추가 없음.
5. **측정(V1)**: K-49 측정 테스트 방식으로 "첫 열기 때 UI 스레드를 막는 최장"을 잰다 — 전/후, 파일은 K-49와 같은 6개(TS 1.56만·4.5만, ash 1.25만·5.7만, 합성 마크다운·HTML), release. 백그라운드 파싱 완료까지 걸린 시간도 함께.
V1 테스트: 큰 텍스트에서 첫 강조가 백그라운드로 가고 결과가 들어온 뒤 runs가 동기 전체 파싱과 같음, 파싱 중 편집/닫기에서 결과 버림.
확인: `cargo build`, `pwsh -NoProfile -File tools/apply-manifest.ps1`, 관련 테스트, `cargo clippy --all-targets -- -D warnings`, `git diff --stat vendor/gpui-base` 비어 있음. 앱 실행·커밋 없음. 보고 `specs/v0.5/cards/K-50.report.md`(전/후 표). 답은 경로만.
