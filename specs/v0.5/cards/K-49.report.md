## 3. 원인과 판단 (가장 작은 변경)
- 전: TypeScript 두 파일만 한 글자에 0.2~1.5초(첫 파싱 5.8~37.7초), 나머지는 한 프레임 안팎. 시간 분해(임시 추적, 제거함): 루트 파싱 1.3ms, 바뀐 범위 계산 1ms, **주입 질의 `refresh`가 95ms**(바뀐 범위 1~2개). 바뀐 범위는 1바이트인데 걸렸다. 주입 쿼리 패턴을 하나씩 꺼 보면 `(comment) @_ecma_comment [(string …) (template_string …)]` 꼴 패턴 6개(html·sql·graphql 등 "앞 주석 + 뒤 문자열")가 각 14ms였다 — tree-sitter가 주석마다 **형제 노드 전부**를 훑기 때문에, 루트(`program`, 최상위 노드 수천 개)에 바로 돌리면 바뀐 범위가 1바이트여도 비싸고 첫 파싱은 제곱에 가깝다(tauri 보고의 "주입 쿼리를 편집마다 전체 트리에" 원인과 같은 종류).
- 고침: 주입 질의를 루트가 아니라 **바뀐 범위에 닿는 최상위 노드마다**(`TreeCursor::goto_first_child_for_byte` + `goto_next_sibling`) 돌린다. 형제 탐색이 한 노드 안에 갇힌다. `Tree::changed_ranges` 방식(바뀐 범위만 질의)은 이미 있었으므로 더하지 않았다. 대가: 루트 자신이나 최상위 형제 둘에 걸친 패턴은 못 잡는다 — 24개 언어 injections.scm에 그런 패턴은 없다(루트 노드 이름으로 시작하는 패턴 없음을 확인; 단위 테스트가 JSDoc·태그된 템플릿 주입이 계속 잡힘을 확인).
- 백그라운드로 옮기지 않은 이유: 고친 뒤 막은 최장이 TS 3.6~8.3ms, Rust 4~26ms, HTML 8ms로 한 프레임(16ms) 안이거나 조금 넘는 정도다. 남은 것은 루트 문법의 증분 파싱 자체다 — 합성 마크다운은 한 글자에 루트 파싱 12~18ms(tree-sitter-md의 블록 파서)이고 파일을 연 뒤 첫 편집 한 번은 55~60ms(이후 반복되지 않음), ash 5.7만 줄은 루트 파싱 25ms. 카드 기준("한 프레임을 크게 넘으면")에 해당하지 않아, Zed식 1ms 동기 + `background_executor` 이동(Rope·트리 소유권, 이전 트리 색 유지, 결과 반영 시점 등 변경이 큼)은 하지 않았다. 5.7만 줄·마크다운 첫 편집에서 체감 지연이 보고되면 그때 `reparse`만 옮기는 별도 카드.
- 첫 파싱은 UI 스레드에서 도는 채로다: TS 4.5만 줄 1.4초, 1.5만 줄 0.4초(전 37.7초·5.8초). 더 줄이려면 첫 파싱도 백그라운드 + 그동안 평문이 필요하다(별도 카드 후보).
