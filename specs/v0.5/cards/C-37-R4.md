# C-37-R4 — 5차(run5-step1~5): 앞 창 얻기 실패 3건, 스크립트 버그 2건
5차 결과(각 `specs/v0.5/verify/reviews/measure-ORDER-09-run5-stepN/log.txt`): 복원·PID 정리는 모두 정상. 입력 가드는 제대로 막았다(다른 창으로 입력 0건).
1. **step1·2·5 `FATAL: setup - Failed to bring app window ... to foreground`**: Windows는 앞 창이 아닌 프로세스(터미널의 pwsh)가 `SetForegroundWindow`로 다른 창을 앞으로 가져오는 것을 막는다(foreground lock). 키 입력으로 우회하는 방법(Alt 키 보내기 등)은 **쓰지 않는다** — 앞 창 확인 전 입력이 되기 때문이다. 대신:
   - **마우스 입력의 가드**를 "그 점의 창(`WindowFromPoint`, 루트는 `GetAncestor(GA_ROOT)`)이 `$script:appHwnd`이고 그 창의 PID(`GetWindowThreadProcessId`)가 띄운 PID"로 바꾼다. 그러면 앱 창이 화면 맨 위에 보이는 곳을 누르는 것은 앱에만 가고, 그 클릭으로 앱이 앞 창이 된다. 점의 창이 다르면(다른 창이 덮음) 입력하지 않고 그 단계 FAIL.
   - **키 입력의 가드**는 지금처럼 `GetForegroundWindow() == appHwnd`. 키를 보내기 전에 앞 창이 아니면, 위 규칙을 지나는 안전한 클릭(예: 상태 바 빈 곳이나 편집기 — 동작에 영향 없는 곳을 단계별로 지정) 1회로 앞 창을 만들고 다시 확인, 그래도 아니면 FAIL.
   - 시작 직후 앱 창이 다른 창에 가려 있을 수 있으니 `ShowWindow(SW_RESTORE)`·`SetWindowPos(HWND_TOP, SWP_NOMOVE|SWP_NOSIZE|SWP_SHOWWINDOW)`(입력 아님)로 z 순서를 올리는 시도는 해도 된다. `HWND_TOPMOST`로 고정하지는 않는다(사용자 창을 가림).
   - setup의 `Ensure-Foreground` 실패를 FATAL로 끝내지 말고 위 클릭 방식으로 진행. 마우스 휠·마우스 뒤로도 마우스 규칙(점의 창 = 앱)과 키 규칙(앞 창 = 앱) **둘 다** 만족할 때만.
2. **step3 `'if' 용어는 cmdlet... 인식되지 않습니다`**: 식 안에 `if`를 쓴 곳(예: 함수 인자나 `-f` 안의 `(if ...)`)을 `$(if ...)` 또는 미리 변수로 바꾼다. 해당 줄을 찾아 보고.
3. **step4 `'modifiers' ... System.Object[] ... System.UInt16`**: `Safe-KeyCombo`에 `@(0x11)`처럼 넘긴 배열이 `[ushort[]]`로 바뀌지 않음. 호출부를 `[ushort[]]@(0x11)`로 하거나 `Safe-KeyCombo`의 매개변수를 `[int[]]`로 받아 안에서 `[ushort[]]`로 바꾼다. 모든 `Safe-KeyCombo` 호출부를 같은 방식으로.
4. 2·3 같은 실행 시 오류를 화면 없이 미리 잡도록: `-DryRun`에서 각 단계 스크립트 블록을 **입력 함수만 기록용 가짜로 바꿔** 실제로 끝까지 실행해 본다(가짜 `Safe-*`는 로그만 남기고 아무것도 보내지 않음, 스냅샷 함수는 run4 `app-stdout.txt` 리플레이 값을 돌려줌). 5단계 모두 PowerShell 런타임 오류 없이 끝나는지 확인(판정값은 의미 없어도 됨).
확인: 파서 구문 검사 0, 4항의 dry-run 5단계 런타임 오류 0, `-DryRun -Out specs\v0.5\verify\reviews\measure-ORDER-09-dryrun5`. 앱·session 실행 금지. 기존 폴더 지우지 않음. 보고 `specs/v0.5/cards/C-37-R4.report.md`. 답은 경로만.
