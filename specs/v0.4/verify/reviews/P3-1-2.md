## Must fix

1. **교체 실패 때 원본과 완성된 임시본을 모두 잃을 수 있다.**
   - 위치: `src/text_io.rs:72–85`, 호출한 `src/state/win.rs:67–96`.
   - 역할: 새 바이트를 같은 폴더 임시 파일에 `create_new`·`write_all`·`sync_all`한 뒤 기존 state 교체 함수를 호출한다. 모든 오류에서 임시 파일을 삭제한다.
   - 문제: `state::win::replace_file`은 `ReplaceFileW`의 backup 인자를 NULL로 전달한다. Windows의 `ERROR_UNABLE_TO_MOVE_REPLACEMENT`(1176)는 이 경우 **원본 파일이 없어지고 교체용 파일은 임시 이름에 남는 상태**를 허용한다. 그런데 `write_file`이 남은 임시본까지 지워 복구할 내용도 없앤다. 성공 경로가 임시 파일을 사용한다는 사실만으로 모든 실패에서 원본 보존을 보장할 수 없다. [Microsoft ReplaceFileW 오류 규약](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew).
   - 기대 수정: 원본 백업·복구를 포함해 부분 교체 실패를 처리하고, 오류 코드·실제 파일 상태를 확인하기 전 마지막 완성본을 무조건 삭제하지 않는다. 원본 보존을 보장할 수 없으면 복구 가능한 파일을 남기고 위치를 알린다. 공유 state helper 변경이 필요하면 lead가 범위를 지정하고 모든 호출부(state 저장·본문 저장)를 확인한다.
   - 기대 검증: 현재 성공 테스트 외에 임시 쓰기 실패·교체 실패·부분 교체 실패 상태를 주입하는 테스트를 추가해 원본 또는 복구 가능한 사본 보존과 정리 대상을 검증한다.
   - 미수정 영향: 저장 실패가 사용자 파일의 완전한 손실로 이어질 수 있다. 이는 P3-2의 데이터 손실 방지 조건에 직접 해당한다.

2. **저장과 reload의 유효성 관리가 분리돼 저장 후 오래된 읽기를 적용할 수 있다.**
   - 위치: `src/ui/pane.rs:231–283` (`finish_read`, `begin_save`, `finish_save`), `src/ui/watch_io.rs:197–263`.
   - 역할: 읽기는 `pending`, 저장은 별도 `saving` 토큰을 쓴다. 읽기 완료는 현재 dirty 여부만 확인한다.
   - 문제 A(D-046 자기 쓰기): A를 B로 편집해 저장한다. 자기 쓰기 감시가 저장 완료 콜백보다 먼저 시작되어 old_hash=A로 B를 읽으면 `Changed(B)`가 된다. 저장 완료가 먼저 hash=B·dirty=false를 적용한 뒤 이 reload가 도착하면 `finish_read`가 허용하고 `set_value(B)`를 다시 한다. gpui-base의 `set_value`는 같은 내용이어도 선택·스크롤·undo를 초기화하므로 자기 저장이 편집 상태를 잃게 한다(`input/base/state.rs:1226–1246`).
   - 문제 B(오래된 내용): A 기준 reload가 외부 B를 읽어 대기 중이고, 사용자가 C를 편집·저장해 hash=C·dirty=false가 된 뒤 `Changed(B)`가 도착해도 pending 토큰은 유효하다. B를 적용해 버퍼를 과거 내용으로 바꾸고 깨끗하다고 표시한다. 이후 저장하면 디스크 C까지 B로 덮을 수 있다. 이 문제는 이후 P3-4의 충돌 표시와 별개로 읽기·쓰기 완료 순서에서 발생한다.
   - 기대 수정: 저장과 읽기가 같은 탭 버전/세대에 연결되도록 하고, 저장 이전 또는 저장 중에 시작된 읽기가 저장 뒤 적용되지 않게 한다. 적용 시점의 디스크 hash가 이미 같은 자기 쓰기는 `set_value`하지 않는다. 저장 시작 때만 pending을 지우면 저장 중 시작한 reload는 남으므로 충분하지 않다.
   - 기대 검증: 자기 쓰기 `Changed(B)`가 save 완료 뒤 도착하는 순서, 과거 B read가 C save 완료 뒤 도착하는 순서를 순수 상태 테스트로 추가한다. dirty가 true인 동안의 단순 거부 테스트만으로 이 순서를 검증할 수 없다.
   - 미수정 영향: 자기 저장 때 undo·커서가 초기화되거나 저장한 최신 내용을 오래된 버퍼로 대체한다.

3. **CRLF 파일에 새 줄을 입력하면 LF가 섞여 저장된다.**
   - 위치: `src/ui/pane.rs:28–46,159–167,256–269`, `src/text_io.rs:1–5,49–66`.
   - 역할: 인코딩 enum만 보존하고 줄 끝은 편집기의 문자열에 남아 있다는 전제로 그대로 encode한다. 탭에는 줄 끝 형식 상태가 없다.
   - 문제: `a\r\nb`를 연 뒤 b 끝에서 Enter를 누르면 gpui-base Editor의 Enter 경로는 `\n`을 삽입한다(`input/base/state.rs:2391–2392`; 다중 커서 경로도 LF). 현재 저장은 이를 그대로 써 `a\r\nb\n`이 된다. 기존 CRLF를 유지하는 것과 새 줄도 기존 형식으로 저장하는 것은 다르다. 현재 왕복 테스트는 decode→encode만 검사해 편집 중 추가된 줄 끝을 놓친다.
   - 기대 수정: 열 때 LF/CRLF 정보를 보존하고 편집으로 추가한 줄도 원래 형식으로 저장한다. 불필요한 기존 바이트 변경을 피하며, 저장 hash와 reload 비교는 실제 편집기 문자열 표현과 일관되게 관리한다.
   - 기대 검증: LF·CRLF 파일을 연 뒤 Enter에 해당하는 편집을 하고 저장한 바이트를 비교하는 테스트를 추가한다. 단순히 원본을 손대지 않고 encode하는 왕복 테스트는 유지하되 이것만으로 R-10의 편집 후 줄 끝 보존을 판정하지 않는다.
   - 미수정 영향: CRLF 파일이 혼합 줄 끝으로 바뀌어 원래 줄 끝 보존 요구를 깨뜨린다.

## R1

결론: REWORK

- 대상: `work/editor` / `fe105620cf338388be06e7bd0c88fd758b6e3fe8`. 시작·종료 HEAD 동일, 작업 트리 차이 없음. 앞선 Must fix 1~3의 수정과 추가 테스트만 확인했다.
- **1 해소:** 임시 쓰기 실패는 교체를 호출하지 않고 정리한다. 교체 오류 후 원본 경로가 있으면 기존 파일을 유지하고, 원본 경로가 사라졌으면 완성된 임시본을 남기며 오류 문구에 복구 경로를 포함한다. 주입 테스트가 일반 실패와 1176 부분 실패를 검증한다. 「항상 원본이 남는다」가 아니라 「원본 또는 복구 가능한 완성본을 남긴다」는 보장으로 인정한다.
- **2 해소:** `finish_read`가 saving 중 결과를 거부하고, `finish_save`가 저장 전·저장 중 시작된 pending 읽기를 무효화한다. 저장 후 시작한 읽기라도 현재 hash와 같으면 `ReadApply::Kept`로 결정한다. 첫 읽기·watch reload 호출부는 Fill인 경우에만 `set_value`하므로 자기 쓰기로 undo·커서를 초기화하지 않는다. 저장 전/중/후의 추가 순서 테스트가 통과했다.
- **3 일반 LF/CRLF는 해소, 혼합 줄 끝 보존은 미해소:** `decode_text`가 Format에 인코딩·LF/CRLF를 저장하고 내부 표현을 LF로 정규화한다. `encode_text`가 새로 입력·붙여넣은 줄을 파일 형식으로 되돌린다. UTF-8 BOM·UTF-16 LE·CP949에서도 통과했다. 그러나 `src/text_io.rs`의 `decode_text`·`encode_text`는 첫 줄 끝을 전체 파일에 적용한다. 예를 들어 기존 `a\r\nb\nc`를 열어 **편집 없이** 저장하면 `a\r\nb\r\nc`가 된다. 이 형식은 유효한 텍스트이며, R-10의 원래 줄 끝 보존을 내부 표현 변경만으로 면제할 수 없다. 소스의 app-value 주석만으로 무편집 파일 변환 정책이 승인된 것은 아니다.
- 기대 수정: 혼합 줄 끝의 무손실 저장을 지원하거나, 지원하지 않는 형식이면 판독 불가 인코딩처럼 편집/저장을 차단하고 알린다. 기존 혼합 형식을 일괄 통일하려면 별도 사용자 결정으로 명시해야 한다. `a\r\nb\nc`와 반대 순서의 혼합 입력에 대해 무편집 저장 바이트가 보존되거나 명시적으로 거부되는 테스트를 추가한다. 동일 LF/CRLF 파일의 정상 저장과 새 줄 형식 보존은 유지한다.

### 내부 LF와 Phase 3 R-15 분류

- 내부 문자열·hash가 LF이고 디스크 저장은 원래 CRLF라는 설계 자체는 일관되며 허용 가능하다. 첫 읽기·watch read의 `decode_text`, 편집·저장 hash의 `buffer_hash`, 저장의 `encode_text` 연결을 확인했다.
- `tools/verify-v02-phase5.ps1:981–984`는 CRLF 문자열의 바이트 길이·FNV를 editor/dev 로그에 직접 대조하므로 예상 차이가 발생한다. **그 차이를 의도한 변경으로 분류하는 판단은 타당하되, 예상 LF 길이·FNV와 실제 읽기 성공을 별도 증거로 남겨야 한다.** 원래 조건을 기다리다 timeout이 나는 것을 통째로 「의도한 실패」로 인정하면 실제 reload 실패까지 가릴 수 있다. 디스크 바이트의 CRLF 보존도 별도로 확인해야 한다. 지난 버전 증거·기대값을 수정하지 않는다.
- 위 혼합 줄 끝 파일의 디스크 내용 변경은 단순 editor FNV 표현 변경과 구분해야 하며, 현재 의도한 변경 분류로 함께 승인됐다고 보지 않았다.
