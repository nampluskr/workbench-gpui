## 1. 수정 내용 및 코드 검토

### 1.1 사이드바 폭 1.25배 확대 원인 분석
- **원인 설명 검증**:
  - `src/ui/mod.rs`의 `resizable_panel_group` 내부에서 사이드바 `resizable_panel()`이 기본적으로 `flex_grow: 1.0`을 가지고 있어, `.size(width)`로 기준 폭(300px 또는 494px)을 지정했음에도 불구하고 컨테이너의 남은 공간을 분배받아 약 1.25배(300 → 375px, 494 → 617px)로 확대되고 있었습니다.
  - 커밋 `2be8a9a`에서는 사이드바 패널에 `.flex_none()`을 명시적으로 추가하여 크기가 고정된 패널이 basis 이상으로 grow하지 않도록 수정했습니다.
  - 이 설명과 해결책은 `gpui-base`의 `ResizablePanel` 레이아웃 동작 메커니즘 및 코드 주석(`A sized panel must not grow`)과 완벽히 일치합니다.

### 1.2 스펙 ID 및 상수 정의 대조
- `src/ui/metrics.rs`:
  - `sidebar["footer.height"]` (A-11.4): `SIDEBAR_FOOTER_HEIGHT` (30px = `rems_from_px(30.)`) 추가.
  - `sidebar["default_width"]` (L-33): 기존 `SIDEBAR_DEFAULT_WIDTH` (300px = `rems_from_px(300.)`) 유지.
  - `sidebar_metrics_equal_spec_exactly` 단위 테스트를 추가하여 `sidebar["default_width"]`, `sidebar["footer.height"]`, `sidebar["footer.padding"]`, `sidebar["footer.gap"]` 값이 `spec/zed-metrics.toml`과 정확히 일치함을 검증하도록 구성했습니다.
- `src/ui/layout.rs`:
  - 사이드바 푸터 요소에 `.h(SIDEBAR_FOOTER_HEIGHT)` 및 `.items_center()`를 적용하여 상단 1px 테두리를 포함한 30px 높이 규격을 충족하도록 했습니다.

### 1.3 다른 레이아웃 영향도 검토
- 사이드바 패널만 `.flex_none()`이 적용되었고, 인접한 메인 작업 공간(`workspace`)은 잔여 가용 폭을 차지하는 flex 구조를 유지하므로 사이드바 외 다른 UI 셸 영역의 배치에 부정적인 영향이 없습니다.
- 사이드바 푸터의 30px 높이는 상태 표시줄 높이(`statusbar["height"]` 30px)와 대칭을 이루며 시각적 일관성을 확보합니다.

## 4. R1 재작업 리뷰 (`e02a6f8`)

- 일자: 2026-11-04
- 대상 커밋: `work/ui` 브랜치 `e02a6f8` (`P2-1-R1: sidebar panel fixed so a container resize does not rescale it (300/494)`)

- 검증 근거: `specs/v0.4/verify/reviews/measure-p2-1-r1.md` (좁은 V3 실측)

### 4.1 고친 이유와 코드 동작 부합성
- **문제 분석**: 첫 구현 커밋 `2be8a9a`에서 적용한 `.flex_none()`은 초기 레이아웃 시점의 확장은 억제할 수 있으나, 앱 실행 후 창이 기본 크기(1536px)에서 최대화(1920px)되는 등 컨테이너 크기가 변할 때 `gpui-base`의 `ResizablePanelGroupState`가 각 패널을 가용 너비 비율에 따라 리스케일(300 -> 375, 494 -> 617, 약 1.25배)하는 동작을 방어하지 못했습니다.
- **해결책 검증**: `gpui-base` 라이브러리의 `ResizablePanel` 구현에 따라 `.fixed()`를 적용했습니다. `.fixed()`가 지정되면 패널에 `fixed: true` 속성이 부여되어, 컨테이너 리사이즈가 발생해도 해당 패널은 지정된 크기를 불변으로 유지하고 잔여 공간은 다른 비고정 패널(`workspace`)에만 분배됩니다. 동시에 "A fixed panel only gives up space to a drag on its own handle" 메커니즘에 의해 핸들 드래그를 통한 크기 조절은 그대로 지원됩니다. 코드 변경 및 주석 설명이 라이브러리 내부 메커니즘과 완벽히 부합합니다.

### 4.2 사용자 폭 저장 및 복원 보존 여부
- 핸들을 드래그하여 사이드바 폭을 변경할 때 트리거되는 `on_resize` 콜백(`this.on_sidebar_resized(w, window, cx)`) 및 `state.json` 저장 로직이 온전히 보존됩니다.
- `specs/v0.4/verify/reviews/measure-p2-1-r1.md`의 `verify-v02-phase3` 회귀 검증에서 사용자가 핸들을 끌어 조절한 폭(300 + 119 = 419px)이 재시작 후 정확히 419px로 복원됨이 확인되었습니다(A-22 통과).

### 4.3 다른 패널 영향도
- `workbench-split` 그룹 내에는 사이드바와 메인 `workspace` 패널만 배치되어 있습니다. 사이드바가 300px 고정 폭을 안정적으로 유지함에 따라, `workspace`는 전체 1920px 중 1620px의 가용 공간을 정확하게 차지합니다. 다른 내부 패널이나 UI 컴포넌트에 어떠한 부정적 영향도 없습니다.
