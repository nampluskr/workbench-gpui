# P3-4a 리뷰

결론: REWORK

What this change does: dirty 탭의 디스크 변경을 충돌 상태로 기록하고 버퍼는 유지한다. 파일 부재를 삭제 상태로 기록하며, 삭제된 비어 있지 않은 버퍼는 저장으로 재생성할 수 있고 저장 성공 후 충돌·삭제 상태를 해제한다.

- 대상: `work/editor` / `f973dcf8133d10bef3532940c31f191f407963c5`, `git diff 646c513..f973dcf`. 시작·종료 HEAD 동일, worktree 소스 변경 없음.
- 기준: V1, R-11, E-086·E-087·D-046. ponytail-review 및 별도 정확성 리뷰. 원문은 `spec/INDEX.md`를 통해 `docs/refs/01-zed/02-INTERACTION.md` 13.4절 E-084~E-087만 확인했다. Zed 앱 소스는 열거나 복사하지 않았다.
- H-16의 P3-4a(상태 로직)·P3-4b(탭 표시) 분리를 따른다. 화면 표시 자체와 P3-3의 저장 확인창 구현은 이 리뷰 범위 밖이다.

## Must fix

1. **충돌 중 원문으로 undo하면 디스크와 다른 버퍼가 깨끗하다고 표시된다.**
   - 위치: `src/ui/pane.rs:102–108,358–364` (`modified`, `has_conflict`, `on_edit`).
   - 역할: dirty는 마지막 읽기/저장 hash와 현재 버퍼를 비교하고, conflict는 `dirty && disk_changed`다.
   - 문제: A를 연 뒤 C로 편집하고, 외부에서 파일이 B로 바뀌어 conflict가 된 상태에서 undo로 A로 돌아간다. `on_edit`는 dirty=false로 만들고 reload를 요청하지 않는다. `has_conflict`·`modified`도 false지만 실제 디스크는 B다. 감시 이벤트는 이미 처리됐으므로 새 이벤트가 없으면 A가 계속 깨끗한 버퍼로 남는다. Ctrl-S도 modified=false라 쓰지 않는다. 소스 shortcut이 이 동작을 인정하지만, 일반적인 undo 사용이 곧 한계를 밟고 E-086의 깨끗한 버퍼 자동 재읽기 요구와 충돌한다.
   - 기대 수정: 외부 변경이 보류된 상태에서 로컬 편집이 사라지면 최신 파일 재읽기를 요청하거나, 최신 디스크와 동기화될 때까지 충돌/수정 상태를 유지한다. `hash`가 최신 디스크라는 전제가 깨진 상태에서 깨끗함을 선언하지 않는다.
   - 기대 검증: A 읽기 → C 편집 → B 디스크 변경 → A로 undo 순서를 추가해 최신 B를 반영하거나 동기화 대기 상태를 유지하는지 확인한다. 다음 임의 이벤트에 의존하지 않아야 한다.
   - 미수정 영향: 디스크와 다른 내용을 정상·미수정 버퍼로 보고 작업하게 된다.

2. **정규화한 내용 hash만으로는 외부 형식 변경을 충돌로 보지 못한다.**
   - 위치: `src/ui/watch_io.rs:220–226`, `src/ui/pane.rs:285–294,318–332`.
   - 역할: reload는 LF 정규화된 문자열 hash만 비교해 Same/Changed를 정한다. dirty 탭은 Same이면 disk_changed를 해제하고 format 갱신 전에 반환한다.
   - 문제: UTF-8·LF 파일 A를 편집 중, 다른 프로그램이 **같은 글자**를 UTF-16 LE BOM 또는 CRLF로 저장한다. 정규화 문자열 hash는 같아 Same이고 conflict=false가 된다. dirty 탭의 기존 format은 UTF-8·LF로 남으므로 다음 저장이 외부 인코딩/BOM/줄 끝 변경을 경고 없이 되돌린다. 이는 같은 바이트로 되돌아온 경우와 다르다.
   - Zed와의 차이: 원문 E-086은 디스크 시각이 마지막 저장 시각보다 늦고 미저장 편집이 있으면 충돌로 본다. 현재 코드는 mtime을 보지 않아 A→B→A에서도 해제한다. **정확히 같은 바이트로 돌아온 경우 내용 손실 위험은 작지만 동작 불일치는 남고, 같은 정규화 텍스트만 돌아온 경우에는 위 형식 변경 손실이 발생한다.** 같은 텍스트 hash를 같은 파일 상태의 증거로 사용할 수 없다.
   - 기대 수정: E-086의 디스크 변경 시각/버전과 마지막 읽기·저장 기준을 추적해 충돌을 판정한다. 해시는 D-046의 불필요한 `set_value` 방지에 계속 쓸 수 있다. 내용 기준 정책으로 바꾸려면 lead의 명시적인 결정과 함께 적어도 인코딩·BOM·줄 끝 변경을 보호해야 한다. 자기 저장은 완료 기준을 갱신해 거짓 충돌을 만들지 않도록 한다.
   - 기대 검증: dirty 상태의 UTF-8→UTF-16 및 LF→CRLF 외부 변경, 동일 텍스트 재쓰기/mtime 변경, 자기 저장 후 이벤트를 테스트한다.
   - 미수정 영향: 실제 외부 변경을 충돌 확인 없이 덮어쓰며 E-086 재현 요구를 충족하지 못한다.

3. **충돌·삭제 상태만 바뀐 완료 경로가 갱신을 알리지 않는다.**
   - 위치: `src/ui/watch_io.rs:255–283`의 `item.ws.update(cx, |ws, _| ...)`와 조기 continue.
   - 역할: `finish_read`가 dirty 탭의 충돌 상태를 바꾸고 Dropped를 반환하거나, 삭제 상태를 바꾸고 Kept를 반환한다.
   - 문제: 이 분기에서는 `set_value`도 `cx.notify()`도 호출하지 않는다. 일반 Modify 이벤트는 `Batch::touches_tree`가 false라 트리 갱신에 의한 notify도 보장되지 않는다(`src/fsops/watch.rs:112–114`). 따라서 패널에 포커스를 둔 채 외부에서 dirty 파일을 수정하면 새 상태를 관찰하는 P3-4b의 탭 UI가 다음 입력/다른 redraw 전까지 상태 변경을 알 수 없다. 삭제 이벤트가 트리를 갱신해도 그 알림은 비동기 읽기 완료 **이전**이므로 삭제 상태 반영 후 알림을 대신하지 못한다.
   - 기대 수정: 상태가 바뀐 workspace나 해당 탭의 소비자에게 완료 시 갱신을 알린다. 버퍼를 채우지 않는 상태 변경도 빠뜨리지 않는다. 상태 변경 여부를 반환해 notify 조건으로 쓰거나 완료 어댑터에서 적절하게 알릴 수 있다.
   - 기대 검증: dirty 충돌·깨끗한 파일 삭제가 Fill 없이도 상태 변경 알림 대상으로 분류되는지 테스트하고 실제 notify 연결을 코드로 확인한다(H-9). 앱을 띄워 확인하는 방식으로 대체하지 않는다.
   - 미수정 영향: 상태 로직이 존재해도 외부 변경 시 충돌 점·지워짐 표시가 즉시 갱신되지 않는다. P3-4b의 별도 표시 구현만으로 해결되지 않는다.

## 통과한 경로와 범위

- 깨끗한 탭의 내용 변경은 Fill로 이어져 기존 `set_value` 경로로 자동 다시 읽는다. dirty 탭에서는 충돌/삭제 상태만 기록하고 Fill하지 않아 편집 내용을 덮지 않는다. 위 undo 전이와 상태 알림의 예외는 별도 지적했다.
- `read_text` 실패 후 `try_exists()==Ok(false)`만 Missing으로 본다. 권한·공유 잠금 등 부재가 확인되지 않은 오류는 Unreadable이며 기존 상태를 유지한다.
- 삭제된 깨끗한 비어 있지 않은 버퍼는 modified가 되어 저장을 시작할 수 있고, 빈 삭제 버퍼는 불필요한 쓰기를 하지 않는다. 삭제 뒤 같은 내용이 돌아오면 deleted가 해제된다.
- 저장 성공은 disk_changed·deleted를 지우며, 저장 중 추가 편집이 있으면 dirty는 유지한다. 실패에서는 이 상태를 지우지 않는다. 기존 저장 중 read 차단·완료 시 pending 무효화와 자기 쓰기 Kept 경로를 유지한다. 관련 기존 테스트도 통과했다.
- E-084/E-085 확인창은 P3-3 담당이다. 이 카드의 `begin_save`가 충돌/삭제 저장을 허용하는 사실만으로 확인창 구현까지 완료했다고 보지 않았다.
- bool 상태·기존 읽기 결과·기존 저장 토큰을 재사용하며 새 의존성은 없다. 위 1번의 shortcut은 일상적인 undo에서 요구를 깨므로 승인된 안전한 단순화로 인정하지 않았다.
