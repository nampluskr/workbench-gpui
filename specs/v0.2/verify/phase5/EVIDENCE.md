## 반영까지 걸린 시간

- `recv_ms`: 바깥 변경 직전 → 감시 스레드가 그 묶음의 첫 이벤트를 받음(빈칸 = 앞 묶음에 붙어 따로 줄이 없음).
- `app_ms`: 바깥 변경 직전 → 앱이 반영한 줄(`watch-applied`·`watch-missing`·`tab-reload`)의 t_ms.
- `seen_ms`: 바깥 변경 직전 → 스크립트가 dev 출력에서 반영을 봄(탭 내용은 300ms 주기 레이아웃 스냅숏으로 보므로 더 늦다).
- 원문에 기준 수치는 없다(SPEC R-24 판정 방법). 사례별 전체 표는 각 폴더의 `latency.md`, 원자료는 `results.json` 의 `latency`.

### 읽는 법

- 감시 스레드는 변경 뒤 2~34ms 안에 이벤트를 받는다(`recv_ms`).
- 앱 반영은 묶기(마지막 이벤트 뒤 150ms 조용함) + 틱(100ms) 때문에 보통 160~290ms 다(C: 출력 실행).
- 1초 안팎의 값은 메인 스레드가 바빠 틱이 늦은 경우다. `[dev] watch-tick-late gap_ms=` 줄이 그 자리에 있다.
  - 원인: `--dev-layout` 스냅숏(한 번에 약 130줄)을 이동식 D: 의 표준출력 파일에 줄마다 써서 매번 약 0.6~1.1초 막혔다.
  - 확인: 같은 최적화 빌드로 표준출력만 C: 에 두자 `watch-tick-late` 0건, 트리·탭 반영 158~288ms(`optimized-stdout-c/`).
  - 디버그·최적화(D: 출력) 모두 스냅숏마다 같은 막힘이 있어 빌드 종류보다 시험 출력의 비용이다. 시험 출력이 없는 실제 실행과는 다르다.
- 폴더가 다시 생김(이름 되돌리기·다시 만들기)은 1초 주기 존재 확인으로 잡는다. 그래서 최대 약 1초다. 디버그 실행의 54ms·293ms 는 확인 주기가 마침 가까웠던 경우다.
- 활성이 아닌 등록 폴더 지우기는 1초 주기 존재 확인 대상이다. 세 실행 모두 `via=event` 로 약 150ms 에 잡혔다. 같은 때 들어온 활성 폴더 이벤트(부모 폴더 수정 알림)가 존재 확인을 함께 돌렸기 때문이다. 다른 이벤트가 없으면 최대 약 1초다.
- 600개 만들기·지우기는 스크립트의 쓰기·지우기 자체가 대부분이다. 마지막 변경 뒤 반영까지는 약 80~200ms 다.

### 감시자 수명 (switch)

- `h1\pa`, `h2\pb` 두 폴더. 감시 중인 폴더의 윗 폴더는 Windows 가 이름 바꾸기를 막는다(감시 핸들). 이것으로 핸들을 실제로 놓았는지 봤다.
- pa 감시 중: `h1` 이름 바꾸기 막힘(`Access … denied`).
- pb 로 전환: `watch-stop folder=pa via=activate`, `watch-start root=pb`. 그 뒤 `h1` 이름 바꾸기 됨.
- 활성이 아닌 pa 의 변경: 1.5초 동안 `watch-applied` 없음. pb 의 변경은 반영.
- 다시 pa: 활성이 아닐 때 생긴 `inactive.txt` 가 트리에, 바뀐 `a.txt` 를 탭이 다시 읽음.
- 활성 pa 해제(Remove): pb 감시로 옮김, `h1` 이름 바꾸기 됨.
- 마지막 pb 해제: `watch-stop via=remove`, 새 감시 없음, `h2` 이름 바꾸기 됨.

### 앱 자신의 작업과 바깥 변경 구분 (own)

- F2 로 `notes.txt` → `renamed.txt`: 그 작업이 일으킨 감시 이벤트는 모두 `own`, `external=0`.
  - 탭을 다시 넣지 않음(`tab-reload` 0), 선택은 `renamed.txt` 그대로, 탭은 `renamed.txt` 하나.
- 앱 작업 직후(3초 안) 다른 경로의 바깥 변경은 `external` 로 세고 반영.
- 인라인 입력 중 바깥 변경: `tree=deferred`, 입력칸·가상 행 그대로, 새 행은 아직 없음(`own-deferred.png`).
  - Escape 로 입력을 끝내면 `watch-refresh via=deferred` 로 새 행이 나타남.

### 폭주 묶기 (flood)

- 600개 만들기: 이벤트 1405개를 반영 6번(최적화 5번)으로 묶음. 256개 넘는 묶음 뒤 `watch-refresh via=settle` 로 한 번 더 다시 읽음. 트리 행 수 = 디스크 파일 수.
- 600개 지우기도 반영 10번 이하로 묶음.

## 만든 것

- `src/fsops/watch.rs`(gpui·notify 와 무관, 단위 시험 4개)
  - `Pending`·`Batch`: 이벤트 묶기. 마지막 이벤트 뒤 150ms 조용하거나 첫 이벤트 뒤 1초면 반영. 2048개 넘으면 경로는 버리고 전부 다시 읽기.
  - `touches_tree`: 루트 안의 만들기·지우기·이름 바꾸기만 트리를 다시 읽게 한다(Modify 제외). `touches_root`: 루트 자신·부모 감시 이벤트는 존재 확인.
  - `renames`: RenameFrom 바로 뒤 RenameTo 를 짝으로.
  - `SelfOps`: 앱 자신의 작업 경로를 3초 기억해 이벤트를 own/external 로 나눈다.
- `src/ui/watch.rs`
  - `sync_watch`: 활성 폴더(경로가 있을 때)만 감시. 루트는 하위까지, 부모는 한 단계(루트 자신의 삭제·이름 바꾸기를 바로 안다). 폴더가 바뀌면 감시자와 받는 쪽을 함께 버리고 새로 만든다. 남은 이벤트도 버린다.
  - 100ms 틱: 이벤트 모으기 → 묶음 반영, 미룬 다시 읽기, 폭주 뒤 한 번 더(500ms 뒤), 1초마다 등록 폴더 존재 확인, `sync_watch`.
  - 묶음 반영: 존재 확인 → 이름 바꾸기 짝 따라가기(펼침·선택·표시·탭 경로) → 트리 다시 읽기(입력 중이면 미룸) → 해당 탭 다시 읽기(내용이 다를 때만 `set_value`, 읽지 못하면 그대로).

  - `project_panel.rs`: `follow_rename`.
  - `mod.rs`: `watch` 필드, 시작 때 감시·틱 시작.

## 판단 (원문에 없음)

- 감시 범위: 활성 폴더 하나(PLAN "활성 폴더와 열린 파일"). 열린 탭은 활성 폴더 안 파일이므로 루트 감시로 덮는다. 활성이 아닌 폴더의 트리·탭은 다시 활성화할 때 읽는다.
- 등록 폴더 존재는 1초마다 확인한다(감시하지 않는 등록 폴더, 드라이브 루트처럼 부모가 없는 폴더, 윗 폴더 이름 바꾸기 대비). 활성 폴더 자신의 삭제·이름 바꾸기는 부모 감시로 바로 잡는다.
- 묶기 150ms / 최대 1초 / 틱 100ms / 폭주 기준 256개·500ms 뒤 한 번 더 / 앱 작업 기억 3초.
- 앱 자신의 작업이 일으킨 이벤트도 트리는 다시 읽는다. 결과가 같아서 보이는 변화가 없고, 작업 직후의 바깥 변경을 놓치지 않기 위해서다. 구분은 dev 출력의 own/external 과 탭을 다시 넣지 않는 것(내용 비교)으로 한다.
- 바깥 이름 바꾸기는 짝이 맞으면 펼침·선택·탭 경로가 새 이름을 따라간다. 짝이 없으면(다른 폴더로 옮김, 탐색기 휴지통) 지운 것과 같다.
- 인라인 입력 중에는 트리를 다시 만들지 않고, 입력이 끝나면 다시 읽는다.
- 탭 다시 읽기는 커서·스크롤을 맨 앞으로 되돌린다(gpui-kit `set_value` 동작). 보기 전용이라 잃는 편집은 없다.

## 알려진 한계

- **감시 중인 폴더의 윗 폴더 이름 바꾸기·옮기기가 막힌다(Windows).** ReadDirectoryChangesW 핸들 때문이다. 활성 폴더와 그 부모를 감시하므로 그 위 폴더들이 해당된다. 다른 폴더로 전환하거나 해제하면 풀린다(switch 사례로 확인). 루트 자신의 이름 바꾸기·지우기는 된다.
- **정션 안 변경은 바로 보이지 않는다.** 펼친 정션 아래에서 대상 경로로 만든 파일도, 정션 경로로 만든 파일도 감시 이벤트가 오지 않았다(관찰 2건, 3초 안 반영 안 됨). 루트 안 다른 변경이 오거나 폴더·창을 다시 활성화하면 전부 다시 읽어 보인다(판정 1건).
- 폴더가 다시 생긴 것은 1초 주기 확인으로 잡는다(최대 약 1초).
- 감시를 만들지 못하면(`watch-start-failed`) 폴더·창 활성 때 다시 읽기만 남는다.
- 시험 조건의 한계: 이동식 D: 에 dev 출력을 쓰는 비용 때문에 1초 안팎의 반영 값이 섞여 있다(위 "읽는 법").
