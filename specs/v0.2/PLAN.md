# PLAN — workbench-gpui v0.2

## 읽는 법과 이 순서에 걸린 규칙

**`R-n`은 v0.2 `SPEC.md`의 요구 번호, `D-n`은 v0.2 `DECISIONS.md`의 결정 번호다.** `G-`는 02-gpui 출발 문서, `L-`·`I-`·`A-`·`E-`는 01-zed 명세의 항목 ID 다.

**Phase 1~2 는 02-gpui 7절 PoC 4단계, Phase 3~5 는 5단계를 나눈 것이다.** v0.2 범위를 PoC 4~5단계로 정한 것은 사용자 결정이다(2026-11-01). 키맵(Phase 1)을 먼저 두는 이유는, 메뉴·툴팁의 단축키 표시(Phase 2)와 사이드바·트리의 키(Phase 3·4)가 모두 키맵 적용 결과에 기대기 때문이다(01-zed A-27.3·A-27.5, 02-gpui G-105 "키·메뉴·툴팁 표시가 모두 여기에 기댄다"). 디스크 감시(Phase 5)는 트리(Phase 4)가 있어야 반영을 확인할 수 있어 마지막에 둔다.

**구현은 사용자가 v0.2 문서를 확정한 뒤에 시작한다.** 초안 질문 11건에 대한 사용자 답(2026-11-01, docs/HERDR-DECISIONS.md D-023)은 `DECISIONS.md` D-2·D-4·D-9~D-17 에, 이어진 탭 편집 질문의 답(D-024)은 D-18 에 반영했다.

**모든 Phase 는 끝날 때 아래 순서를 밟는다.** v0.1 PLAN 과 같다(출처: docs/HERDR-SETUP.md 4절과 사용자 지시).

1. wg-reviewer(Codex)가 그 Phase 의 `git diff`를 적대적으로 리뷰한다(최대 2회).
2. wg-checker 가 그 Phase 에 대응하는 R-n 을 SPEC 의 판정 방법대로 검증한다. 01-zed 일치도 대조를 포함하며, 보고서는 `specs/v0.2/verify/phaseN/`에 남긴다.
3. `PROGRESS.md`에 무엇을·결과·검증을 기록한다.
4. Phase 단위로 커밋한다.

**미해결 실패가 있으면 다음 Phase 로 넘어가지 않는다.** 리뷰나 검증에서 해결하지 못한 실패가 남으면 다음 Phase 를 시작하지 않는다. 그때는 작업을 멈추고 사용자에게 올린다. (v0.1 PLAN 과 같은 규칙, 사용자 결정 2026-10-31)

**작업을 끝낼 때마다 `PROGRESS.md`에 기록한다(루트 AGENTS.md 규칙).** 계획 밖 작업은 PROGRESS 의 사용자 요청 작업으로 적는다.

**빌드할 때마다 `tools/apply-manifest.ps1`을 다시 실행한다**(v0.1 "버전 종료" 남은 것 5).
