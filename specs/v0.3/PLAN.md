# PLAN — workbench-gpui v0.3

## 읽는 법과 이 순서에 걸린 규칙

**번호와 이름**
- `R-n`은 v0.3 `SPEC.md`의 요구 번호, `D-n`은 v0.3 `DECISIONS.md`의 결정 번호다. 지난 버전 번호는 `v0.2 R-n`처럼 쓴다.
- 카드 ID
  - `P<Phase>-<번호>`는 초안 PLAN의 카드 번호다(예: P0-1, P2-3). 데스크톱 환경 카드는 `P0-0a`처럼 붙인다.
  - `F<번호>`는 초안 FINALIZE의 단계 번호다.
  - rework 카드는 원래 ID에 `-R1`, `-R2`를 붙인다.
- 담당 이름(`lead`·`spec`·`reviewer`·`impl-ui`·`impl-editor`)과 모델은 `HERDR-SETUP.md` 1장을 따른다.
- 검증 수준 `V0~V4`는 루트 `AGENTS.md` 3A.1을 따른다. 카드의 검증 칸이 "-"이면 코드를 바꾸지 않는 카드다.

**Phase 0~3은 초안 PLAN의 P0~P3이다**(D-2, 사용자 결정 2026-11-03).
- 초안 P0에 다음 둘을 합쳐 하나의 Phase 0으로 만들었다.
  - 데스크톱 환경·v0.2 동작 점검
  - FINALIZE F0~F5
- 초안 P4~P6은 v0.4 이후로 간다(맨 아래 절).

**순서의 이유**
- Phase 0이 맨 앞인 이유는 두 가지다.
  - v0.1·v0.2는 노트북에서 만들었다. 데스크톱에서 같은 결과가 나오는지 먼저 확인해야 한다(사용자 지시 2026-11-03).
  - 감사 결과와 수치 스펙 파일이 이후 모든 Phase의 입력이다.
- Phase 1(검증 기반)이 Phase 2보다 앞이다. 레이아웃 테스트와 덤프가 있어야 Phase 2·3의 변경이 값을 바꾸지 않았는지 싸게 확인할 수 있다(초안 P1 목표).
- Phase 2(상수·테마)가 Phase 3(공통 컴포넌트)보다 앞이다. 스타일 체인을 합치기 전에 그 안의 수치를 상수로 바꿔 두어야 같은 체인인지 가릴 수 있다.

**Phase 진행 규칙**(초안 PLAN 2.1)
- Phase는 순서대로 진행한다. 이전 Phase의 완료 조건을 통과해야 다음 Phase를 시작한다.
- 같은 Phase 안에서 `impl-ui`와 `impl-editor`는 서로 다른 범위를 병렬로 진행할 수 있다. 단, `impl-editor`는 에디터 코어 카드가 있을 때만 띄운다(HERDR-SETUP 1.1).
- Phase 1~3은 리팩토링 Phase다. 동작을 바꾸지 않는다. 동작 변경이 필요하면 멈추고 사용자에게 올린다(v0.4 이후 카드 후보).
- Phase 진행 중 계획 변경이 필요하면 `lead`가 사용자에게 보고하고, 승인 후 이 문서를 고친다.

**Phase 시작 때 (`lead`)**(초안 PLAN 2.2)
1. 이 문서의 해당 Phase 절을 기준으로 작업 카드를 `specs/v0.3/agents/TASKS.md`에 쓴다(형식은 HERDR-SETUP 5.1).
2. 작업 카드마다 검증 수준(V0~V3)을 지정한다. 기본값은 V0다.
3. 작업 카드 목록을 사용자에게 보고하고, 승인 후 지시를 시작한다.

**Phase 종료 때 (`lead`)**(초안 PLAN 2.3, v0.1·v0.2 규칙 포함)
1. v0.2 검증 스크립트 전체를 다시 돌려 기준선과 대조한다(R-12). Phase 0은 기준선을 만드는 Phase라 제외한다. 대상은 P0-0c와 같은 9개이고, 기준선은 `verify/baseline/`의 데스크톱 결과다(phase3 R-28 폭 실패 2건 포함, F5 Q-15).
2. 그 Phase에서 바뀐 화면과 쌓인 "실측 필요" 항목을 묶어 V3 작업 카드를 만든다.
3. V3 결과의 불일치는 rework 카드로 처리하고, 불일치 항목만 다시 측정한다.
4. "사용자 확인 필요" 항목을 모아 사용자에게 한 번에 전달한다(V4).
5. `/ponytail-debt`로 의도적 단순화 목록(`shortcut:` 주석)을 점검한다.
6. `specs/v0.3/agents/HANDOFF.md`와 `PROGRESS.md`를 갱신하고, Phase 단위로 커밋한다. git 태그는 `v0.3-phase-<번호>`로 남긴다.
7. 완료 조건을 채웠는지 사용자에게 보고하고, 승인 후 다음 Phase로 넘어간다.
8. 미해결 실패가 있으면 다음 Phase로 넘어가지 않고 멈춘다.

**모든 작업에 걸리는 규칙**
- 작업을 끝낼 때마다 `PROGRESS.md`에 무엇을·결과·검증(수준 포함)을 기록한다. 계획 밖 작업은 사용자 요청 작업으로 적는다(루트 `AGENTS.md`).
- 빌드할 때마다 `tools/apply-manifest.ps1`을 다시 실행한다.
- 지난 버전 폴더에는 쓰지 않는다. `tools/verify-v02-*.ps1`은 항상 `-OutDir specs\v0.3\verify\...`로 돌린다.
