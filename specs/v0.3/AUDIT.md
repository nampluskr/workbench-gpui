## Must fix

### 1. 복사 대상 이름 확보와 쓰기가 분리되어 기존 파일을 덮어쓸 수 있다

- 위치: `src/fsops/ops.rs:30`, `:122`, `:136`, `:164`; 호출 `src/ui/panel_ops.rs:152`, `:191`.
- What this is: 붙여넣기·Duplicate는 `paste_path`로 아직 없는 이름을 고르고 `copy_entry`로 복사한다.
- Problem: 이름 확인 뒤 다른 프로그램이 같은 대상 파일을 만들면 `fs::copy`가 그 파일을 덮어쓴다. 디렉터리의 `create_dir`와 달리 파일 복사에는 배타적 생성 보호가 없다. 복사 중 새로 추가되는 하위 파일도 같은 경로 경쟁이 가능하다.
- Fix: 공통 파일 복사 지점에서 `create_new(true)`로 목적 파일을 배타적으로 만들고 스트림을 복사한다. 이미 존재하면 덮어쓰지 않고 오류로 돌려준다. 이 경우를 잡는 최소 테스트가 필요하다.
- If we skip it: 외부 프로세스와 대상 이름이 겹치면 사용자가 이미 가진 데이터가 확인 없이 바뀐다.

### 2. 다른 볼륨 이동은 복사 도중 생긴 원본 변경을 삭제할 수 있다

- 위치: `src/fsops/ops.rs:208–225`; 호출 `move_entry` → `src/ui/panel_ops.rs:154`.
- What this is: 다른 드라이브로 잘라 붙이기는 원본 요약 → 복사 → 대상 요약 대조 → 원본 삭제 순서다.
- Problem: 복사한 파일 A를 외부 프로그램이 이후 수정해도 최초 파일 수·폴더 수·바이트와 대상 요약은 그대로 같을 수 있다. 비교는 복사 뒤 원본을 다시 보지 않으므로 최신 A가 원본 삭제로 사라진다. 복사 후 원본에 새 파일이 추가되는 경우도 같다. 기존 정상 이동 테스트는 동시 변경을 다루지 않는다.
- Fix: 최소한 복사 전후 원본의 파일 목록·정체·크기·수정 상태를 대조해 변경 시 원본을 남기고 오류로 끝낸다. 삭제 직전까지의 경쟁까지 막는 보장 범위는 별도 결정해야 한다. 요약 재조회만으로 완전한 보호라고 주장하면 안 된다.
- If we skip it: 앱 밖에서 저장한 최신 내용이 다른 볼륨 이동 도중 유실될 수 있다.

## Should fix

### 3. 붙여넣기·복제의 일반 오류는 사용자에게 표시되지 않는다

- 위치: `src/ui/panel_ops.rs:140–205`, `:26–40`.
- What this is: 복사·이동 결과를 `log_fs`에 전달하고 성공한 대상만 선택한다.
- Problem: 대상 쓰기 권한 거부·디스크 부족이면 개발 플래그가 없는 일반 실행에서 오류가 보이지 않는다. 링크 포함 교차 볼륨 이동만 알림이 있고, cut 클립보드는 실패한 항목까지 전부 비워진다.
- Fix: 이미 있는 `notify` 또는 삭제 실패의 집계 알림 패턴을 재사용해 일반 실패를 알리고, 실패한 cut 항목을 다시 시도할 수 있도록 남긴다. 부분 성공·부분 실패 테스트가 필요하다.
- If we skip it: 사용자는 왜 작업이 안 됐는지 모르고 잘라내기를 다시 해야 한다. 부분 복사 파일이 남은 상태도 알아차리기 어렵다.

### 4. 큰 파일 첫 열기와 복사·이동이 UI 스레드를 막는다

- 위치: `src/ui/pane.rs:45–79`, `src/ui/panel_nav.rs:286–302`, `src/ui/panel_ops.rs:140–205`.
- What this is: 이벤트 핸들러가 파일 전체 읽기 또는 재귀 복사·교차 볼륨 이동을 동기로 수행한다.
- Problem: 네트워크 경로의 읽기가 지연되거나 큰 폴더를 복사하는 동안 창 입력과 다시 그리기가 멈춘다. 감시 재읽기는 `watch_io.rs:200–240`, 삭제는 `panel_delete.rs:133`에서 이미 백그라운드 작업 패턴을 쓴다.
- Fix: 기존 background executor 패턴을 재사용하고 완료 시 대상 workspace·요청의 정체가 유효한지 확인해 반영한다. Editor의 set_value는 UI에 남긴다. 여러 작업의 동시 실행·취소 정책은 사람이 정해야 한다.
- If we skip it: 흔한 대용량 파일 작업이나 느린 저장장치에서 앱이 응답 없음으로 보인다. 실측 성능 수치는 이번 카드에서 측정하지 않았다.

### 5. 창 닫기 버튼과 팝업 그림자 색이 테마를 우회한다

- 위치: `src/ui/title_bar.rs:31–34`, `:198–205`; `src/ui/tooltip.rs:161–177`.
- What this is: 닫기 hover/active RGB와 검정 그림자 알파를 렌더 코드에서 직접 만든다.
- Problem: 테마 경유 규칙을 지키려면 이 두 경로를 따로 수정해야 한다. 닫기 버튼의 명시 색과 다크/라이트 그림자 분기는 각각 스펙 의미가 있으므로 일반 hover 색으로 대체하면 안 된다.
- Fix: L-84, L-211·L-212의 의미별 테마 토큰으로 현재 색·알파를 그대로 옮긴다. 기존 `elevation_2_shadow` 재사용은 유지한다.
- If we skip it: 이후 테마 매핑 때 일부 색만 예전 값에 남기 쉽다.

### 6. 수치가 여러 모듈의 로컬 상수와 인라인 스타일에 흩어져 있다

- 위치: `src/ui/app_menu.rs:38–65`, `src/ui/panel_view.rs:34–53`, `src/ui/tooltip.rs:28–44`, `src/ui/title_bar.rs:83,105`, `src/ui/folders.rs:760,820–854`, `src/ui/panel_menu.rs:221–222`.
- What this is: 메뉴·트리·툴팁의 크기·간격·시간 중 일부는 이름 있는 로컬 상수이고 일부는 렌더 안 리터럴이다.
- Problem: `metrics.rs`가 있어도 모든 UI 수치가 거기를 거치지 않는다. 예를 들어 메뉴 행 rounding 4와 폴더 패널 padding 8은 사용하는 자리에서만 찾을 수 있다. 로컬 상수도 아직 toml의 확정 ID를 참조하지 않는다.
- Fix: 확정된 스펙 ID별 상수로 이동하되 현 코드 값은 보존한다. `metrics.rs:15–79`의 기존 상수도 ID 대응을 점검한다. 서로 다른 ID를 값이 같다는 이유로 합치지 않는다.
- If we skip it: Phase 2의 수치 단일 관리 목표를 달성하지 못한다. 상세 검색 목록은 `verify/reviews/p0-2-literals.log`에 남겼다.

### 7. 프레임워크의 글자 크기 별칭에도 수치 의존이 숨어 있다

- 위치: `src/ui/title_bar.rs:106`, `src/ui/layout.rs:175,205,381`, `src/ui/folders.rs:762,825,835,855`, `src/ui/panel_view.rs:309`.
- What this is: 여러 화면이 `.text_sm()`·`.text_xs()`로 글자를 그린다.
- Problem: 이 호출은 앱 스펙 상수를 거치지 않고 프레임워크 기본 크기를 선택한다. 이후 명시적 수치만 감사하면 해당 글자 크기를 빠뜨린다.
- Fix: 각 화면의 확정 스펙 ID와 현 프레임워크 값을 대조한 뒤 현재 값 그대로 명시 상수로 연결한다. 이번 감사에서는 새 숫자를 추정하거나 불일치를 판정하지 않았다.
- If we skip it: 스펙 기반 폰트 치수 관리에서 일부 화면이 빠진다.

### 8. 앱 메뉴와 컨텍스트 메뉴의 행·팝업 스타일이 반복된다

- 위치: `src/ui/app_menu.rs:694–788`, `src/ui/context_menu.rs:240–323`.
- What this is: 목록의 최소 폭·padding·스크롤, 구분선, 행 margin·padding·글자·단축키 열, 팝업 테두리·그림자를 각자 조립한다.
- Problem: 같은 메뉴 외형을 바꿀 때 두 체인을 함께 수정해야 한다. 이미 context_menu가 app_menu의 수치 상수를 가져오므로 공유 수치와 중복 스타일의 경계가 어긋나 있다.
- Fix: 동일한 행 바탕·팝업 바탕만 작은 공통 함수로 추출한다. enabled 상태, 이벤트, 포커스, probe ID는 각 메뉴에 남긴다. ID별 수치 차이는 유지한다.
- If we skip it: 한쪽 메뉴에만 스타일 변경이 적용될 수 있다.

### 9. 두 메뉴가 chord 대기·접두 해석 상태 처리를 복제한다

- 위치: `src/ui/app_menu.rs:505–668`, `src/ui/context_menu.rs:334–449`.
- What this is: 입력 접두 보관, 열기 전 컨텍스트에서 바인딩 해석, 1초 타이머 token, 접두 재처리, 50ms 예약을 각자 구현한다.
- Problem: 같은 단축키 해석 수정이 두 곳에 필요하다. 다만 앱 메뉴는 액션 객체를 예약하고 컨텍스트 메뉴는 항목 인덱스를 예약하며 F10 처리도 다르므로 두 컴포넌트를 통째로 합치면 동작이 바뀔 수 있다.
- Fix: 공통 입력 해석과 대기 상태만 먼저 추출하고 실행·닫힘·포커스는 각자 유지한다. 기존 D-032·D-033 세대 보호와 비활성 항목 규칙을 테스트로 보존해야 한다.
- If we skip it: 한쪽의 단축키 버그 수정이 다른 쪽에서 누락될 수 있다. gpui-kit 메뉴로 즉시 대체할 근거는 없다.

- 저장소 전체 구조·직접 의존성·소스 검색을 수행했다. 깊게 읽은 경로는 위 근거에 적힌 파일 작업·상태 저장·키맵 파서·트리 구성·탭 읽기·감시 재읽기·메뉴다. tools는 실행 플래그와 호출을 검색하고 매니페스트 스크립트를 읽었으며, 모든 검증 스크립트 본문을 줄 단위로 감사하지 않았다.
