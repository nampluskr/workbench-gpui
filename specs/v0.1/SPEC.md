# SPEC — workbench-gpui v0.1

## 공통 판정 방식

이 절은 아래 모든 요구의 판정 방법에 공통으로 적용한다.

- 판정은 wg-checker가 한다. 결과는 `specs/v0.1/verify/`에 보고서로 남긴다.
- 화면 요구(1·3단계)의 증거는 두 가지다.
  - 앱 실행 스크린샷. 기준 화면과 같은 창 크기·배율로 찍는다. 기준은 A-30.1·A-30.2(창 1440×852 논리 px, 배율 200%, 이 배율은 가정)와 A-30.6(최대화하지 않은 Latte 화면)이다.
  - 측정값(px, hex). 01-zed 항목 ID별로 기대 값과 나란히 적는다.
- 치수 판정의 기준은 소스 값(L-)이고, 기준 화면 이미지로 잰 값은 보조 증거다(A-30.2). 치수 허용 오차는 ±1 논리 px다(A-31.1).
- 판정은 항목마다 통과/실패로 적는다(A-30.5).
- 2단계(편집기 PoC) 요구의 증거는 PoC 결과 판정표다. 열은 `항목 / gpui-kit 지원 / 직접 구현 필요 / 증거`다.

## R-1. 커스텀 타이틀 바에서 Windows 창 동작이 된다

**요구**

앱이 그린 타이틀 바(L-81)에서 Windows 창 동작이 OS 타이틀 바와 같이 되는지 확인한다.

**정해진 결과**

다음 다섯 가지가 각각 된다.

- 최대화 버튼에 마우스를 올리면 Windows 스냅 레이아웃 플라이아웃이 나온다(G-103, L-83).
- 타이틀 바를 더블클릭하면 최대화되고, 다시 더블클릭하면 복원된다(G-103).
- 타이틀 바를 끌면 창이 이동한다(G-103, L-81).
- 창 테두리를 끌면 크기가 바뀐다(G-103).
- 창을 최소 크기 360×240보다 작게 줄일 수 없다(G-103).

**판정 방법**

공통 판정 방식을 따른다. 다섯 동작마다 실행 스크린샷(스냅 플라이아웃, 최대화 전후, 이동 전후, 크기 변경 전후, 최소 크기에서의 창 크기 측정값)을 남기고 통과/실패를 적는다.

**출처**

## R-2. 타이틀 바와 창 버튼이 Zed 치수·모양·색과 같다

**요구**

타이틀 바 높이, 창 버튼 크기·글리프·색이 Zed 명세와 같다.

**정해진 결과**

- 타이틀 바 높이가 32 논리 px다(L-21, A-32.1).
- 창 버튼이 최소화·최대화(또는 복원)·닫기 순서로 오른쪽 끝에 있고, 각 36×32, 글리프 10px다(L-39, L-83, A-32.2).
- 글리프 글꼴은 Windows 11에서 `Segoe Fluent Icons`다. 코드포인트는 최소화 U+E921, 최대화 U+E922, 복원 U+E923, 닫기 U+E8BB다(L-83).
- 최대화하지 않으면 가운데 버튼이 최대화 □(U+E922), 최대화하면 복원(U+E923)이다(L-312).
- 닫기 버튼 hover 배경이 `#E81120`이고 글자가 흰색이다(L-84).

**판정 방법**

공통 판정 방식을 따른다. 최대화 상태와 최대화하지 않은 상태의 스크린샷, 타이틀 바·창 버튼 치수 측정값(px), 닫기 hover 배경 색 측정값(hex)을 L-21·L-39·L-83·L-84·L-312 ID별로 대조한다.

글리프는 두 가지로 확인한다(L-83).

- 코드 근거: 창 버튼을 그리는 코드에서 글꼴 이름이 `Segoe Fluent Icons`이고, 네 버튼의 문자가 U+E921·U+E922·U+E923·U+E8BB인 위치(파일·줄)를 보고서에 적는다.
- 렌더 확인: 최대화 전후 스크린샷의 창 버튼 글리프를 같은 글꼴·코드포인트로 그린 기준 글리프와 나란히 놓아 모양이 같은지 적는다.

**출처**

D-9 · G-030 · L-21 · L-39 · L-83 · L-84 · L-312 · A-32.1 · A-32.2 · 02-gpui 7절 1단계("32px 확인")

## R-3. 최대화하지 않은 창은 둥근 모서리와 테두리를 갖고, 최대화하면 없어진다

**요구**

창 모서리와 테두리를 Zed 방식대로 그린다.

**정해진 결과**

- 최대화하지 않은 창에서, 화면 가장자리에 맞닿지 않은(tiled 아닌) 변마다 1px 테두리가 있고 모서리가 10px로 둥글다. 맞닿은(tiled) 변에는 테두리와 둥글림이 없다(L-311, G-103).
- 최대화한 창은 변이 모두 맞닿은 것으로 보아 둥글림과 테두리가 없다(L-311, G-103). L-311은 Windows 최대화의 장식 처리를 추정으로 적었다.

**판정 방법**

공통 판정 방식을 따른다. 최대화하지 않은 창, 한쪽 변을 화면 가장자리에 맞붙인(스냅한) 창, 최대화한 창의 스크린샷을 남기고, 변마다 모서리 반지름·테두리 폭 측정값(px)을 L-311과 대조한다. 최대화하지 않은 상태는 A-30.6의 Latte 기준 화면과 비교한다.

**출처**

D-9 · G-030 · G-103 · L-311 · A-30.6 · 02-gpui 7절 1단계

**이후 변경** — Phase 1 구현 중 leader 결정(위임 권한, docs/HERDR-DECISIONS.md D-010)으로 바꿨다(2026-10-31). gpui-pre 0.3.10의 Windows 창은 `window_decorations()`를 재정의하지 않아 장식이 항상 `Decorations::Server`다(gpui-pre `src/platform.rs` 기본값). 창 테두리·모서리는 OS(DWM)가 그리고 앱은 그리지 않는다. 04-APP-SPEC A-30.6은 "앱이 그리지 않는 창 테두리·모서리는 판정 대상이 아니다(OS 몫)"라고 적었다. 그래서 L-311의 1px 테두리·10px 둥글림은 판정 대상에서 뺀다. 대신 OS가 그린 모서리·테두리의 관찰값(최대화 전후 스크린샷, 측정 px)을 보고서에 기록하면 이 요구는 통과다.

## R-4. 배율 100·150·200%와 배율이 다른 모니터 사이 이동에서 타이틀 바가 32 논리 px다

보고서에 위 네 가지가 모두 있으면 통과다. exe에서 추출한 매니페스트 원문을 증거로 붙인다.

## R-12. 레이아웃 뼈대가 Zed 화면 구조와 같은 배치로 서 있다

**요구**

사이드바·Dock·Pane·탭 바·상태 표시줄의 뼈대를 Zed 화면 구조대로 배치한다(A-36.1). 우리 앱이 두지 않는 오른쪽 사이드바·오른쪽 Dock·아래 Dock은 없다.

**정해진 결과**

- 창 최상위가 가로로 [왼쪽 사이드바] → [Workspace]다. 오른쪽 사이드바는 없다(L-11).
- 사이드바가 타이틀 바 줄까지 창 전체 높이를 차지하고, Workspace의 타이틀 바는 사이드바 오른쪽에서 시작한다(L-12).
- Workspace가 세로로 타이틀 바 → 본문 → 상태 표시줄이다(L-13).
- 본문이 가로로 왼쪽 Dock → 가운데다. 오른쪽 Dock과 아래 Dock은 없다(L-14).
- 가운데 영역의 Pane이 탭 바 + 활성 아이템 자리로 되어 있다(L-15).
- 왼쪽 Dock 오른쪽에 테두리(`border_r_1`)가 있다(L-16).

**판정 방법**

공통 판정 방식을 따른다. 기준 화면과 같은 창 크기·배율의 스크린샷에서 영역 배치를 L-11~L-16 ID별로 대조한다.

## R-14. 사이드바와 Dock의 리사이즈가 Zed 규칙대로 된다

**요구**

왼쪽 Dock은 Zed의 핸들·폭 한계 규칙을 따른다. 사이드바는 폭 범위 규칙만 따른다.

**정해진 결과**

- 왼쪽 Dock의 리사이즈 핸들이 6px이고 테두리 위에 절반씩 걸치며, 커서가 `col_resize`다(L-30).
- 왼쪽 Dock 핸들을 더블클릭하면 기본 폭 240으로 돌아간다(L-30, L-32).
- 왼쪽 Dock 폭의 하한은 6px, 상한은 창 폭 − 6이다(L-31. 반대쪽 Dock은 없다).
- 사이드바 초기 폭은 300이고, 끌어서 바꿀 때 200~800 안에서만 바뀐다(L-33).
- 사이드바 핸들의 위치·너비·커서·더블클릭 동작은 이번 요구에 넣지 않는다. 04-APP-SPEC A-11.12가 이를 미확인으로 두고 Dock 핸들(L-30)과 같다고 가정하지 않는다고 적었다(A-40.12).

**판정 방법**

공통 판정 방식을 따른다. 끌기 전후·더블클릭 후의 스크린샷과 폭 측정값(px)을 L-30·L-31·L-32·L-33과 대조한다.

## R-15. rem 헬퍼가 rem 16px를 기준으로 치수를 낸다

**요구**

Zed의 rem·간격 규칙을 재현하는 rem 헬퍼를 둔다. 창의 rem은 `ui_font_size`(기본 16px)다.

**정해진 결과**

- 창의 rem이 16px다(L-01).
- R-13의 치수가 rem 헬퍼를 거쳐 나온다.

**판정 방법**

다음 세 가지가 모두 맞으면 통과다.

- gpui가 로그로 출력한 창 rem 값(A-30.4 "gpui는 로그로 치수 출력")이 16이다.
- 코드 근거: R-13 표의 치수 상수가 각각 rem 헬퍼 호출로 정의되어 있다. 보고서에 A-32 ID마다 정의 위치(파일·줄)를 적고, px 값을 직접 쓴 상수가 있으면 그 위치를 적는다. 그런 상수가 하나라도 있으면 실패다.
- R-13의 측정이 통과한다.

**출처**

D-8 · G-003 · L-01 · 02-gpui 7절 3단계("rem 헬퍼")
