# PLAN — workbench-gpui v0.1

## 읽는 법과 이 순서에 걸린 규칙

**`R-n`은 v0.1 `SPEC.md`의 요구 번호, `D-n`은 v0.1 `DECISIONS.md`의 결정 번호다.** `G-`는 02-gpui 출발 문서(D:\projects\docs\guides\zed-like-editor\02-gpui\README.md)의 항목 ID다.

**Phase 1~3은 02-gpui 7절 PoC 1~3단계를 그 순서대로 따른다.** v0.1 범위를 PoC 1~3단계로 정한 것은 사용자 결정이다(2026-10-31). 편집기 PoC(Phase 2)를 레이아웃 뼈대(Phase 3)보다 앞에 두는 것은 02-gpui 6절의 대응과 맞는다. G-131은 "G-101 PoC를 맨 먼저", G-132는 "G-100을 첫 주에 확인"으로 적었다. gpui-kit Editor가 모자라면 편집기 요소를 직접 써야 하고(G-131), 한글 IME가 안 되면 주 사용이 불가하기 때문이다(G-132).

**Phase 0은 사용자 결정(2026-10-31)으로 넣는다.** 02-gpui 7절에 없는 단계다. D-3·D-4를 실행할 수 있게 하는 준비만 담는다.

**모든 Phase는 끝날 때 아래 순서를 밟는다.** 출처는 docs/HERDR-SETUP.md 4절(에이전트 역할)과 사용자 지시다.

1. wg-reviewer(Codex)가 그 Phase의 `git diff`를 적대적으로 리뷰한다.
2. wg-checker가 그 Phase에 대응하는 R-n을 SPEC의 판정 방법대로 검증한다. 01-zed 일치도 대조를 포함하며, 보고서는 `specs/v0.1/verify/`에 남긴다.
3. `PROGRESS.md`에 무엇을·결과·검증을 기록한다.
4. Phase 단위로 커밋한다.

**미해결 실패가 있으면 다음 Phase로 넘어가지 않는다.** 리뷰나 검증에서 해결하지 못한 실패가 남으면 다음 Phase를 시작하지 않는다. 그때는 작업을 멈추고 사용자에게 올린다. (사용자 결정, 2026-10-31)

**작업을 끝낼 때마다 `PROGRESS.md`에 기록한다(루트 AGENTS.md 규칙).** 계획 밖 작업은 PROGRESS의 사용자 요청 작업으로 적는다.

## Phase 0 — 프로젝트 뼈대

**목적** — cargo 프로젝트를 만들고 gpui-kit을 고정 버전으로 넣어 빌드·실행되는 상태를 만든다. 02-gpui 7절에 없는 준비 단계이고, 사용자 결정(2026-10-31)으로 넣는다.

**대응** — 직접 대응 요구 없음 — D-3·D-4를 실행 가능하게 하는 준비. 관련: `D-3` · `D-4` · G-118 · G-121

**완료 조건**
- 레포 루트에 cargo 프로젝트(`Cargo.toml`)가 있다.
- `Cargo.toml`의 의존성에 `gpui-kit = "=0.8.1"`이 있고, `gpui`·`gpui-pre`를 직접 넣은 줄이 없다(D-3).
- `Cargo.lock`이 커밋되어 있다(D-4).
- G-121 빌드 준비물(MSVC, Windows SDK, CMake)의 설치 여부와 Rust 버전이 PROGRESS에 기록되어 있다. Rust 버전이 1.90(crates.io `rust_version`)과 1.92(설치 문서) 둘 다 이상인지 적혀 있다.
- `cargo build`가 성공하고, 실행하면 창이 뜬다. 빌드 출력과 실행 스크린샷이 증거로 남아 있다.
- 위의 Phase 끝 순서(리뷰 → 검증 → PROGRESS → 커밋)를 마쳤다.
